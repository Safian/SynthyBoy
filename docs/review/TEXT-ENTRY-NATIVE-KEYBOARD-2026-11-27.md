# Native text input for Macro rename / LFO shape name (MPC expert review, 2026-11-27)

Sources used: active SDK `/Users/szabi/.local/share/local-worker/ext/mpc-sdk/` (git febd2ca; the knowledge-base copies `docs-official/mpc-sdk` and `sources/runtime-sdk-docs` carry the same 6.12 text), project `docs/dsp-knowledge/native-text-entry.md`, evidence dir `.hw-local/mpc-perf/native-text-contract-xl-20261124/`, repo worktree gepekere-fresh-version-65be77. Device checked: none (read-only). Key 61 binary: never inspected.

## 1. What the SDK says about TextEditOverlay
- `docs/ui-reference.md` 6.12 (line 1201-1214): "`TextEditOverlay` shows a keyboard (meaningful only for text-valued handles, which third-party VST parameters are not)". Section is headed "less tested". Data shape: `actions[Focus Lost]`, `handleName: Data` (+ `withNumbers` in the factory file). Handle accepted = a text-valued handle. VST parameters (`Parameter N`) are floats 0..1 (host-contract.md line 55), so they are not.
- Nothing is said about what happens on Enter. Only the factory file/binary tells: submit callback -> handle helper -> string setter (see 2).
- FACT (official, host-contract.md:58-59): "The host ... does not use the extended parameter properties; it does not call the text-to-value opcode either." So effString2Parameter (27) is never sent by the host: numeric/text entry for a parameter does NOT go through effString2Parameter. (The SDK framework mpc_plugin.h:679 handles it only for hosts that send it.)

## 2. Evidence for "the host drops the text for third-party plugins"
- FACT (own offline binary inspection, XL `/usr/bin/MPC` 3.10.1.12 (f088e9c8427), sha256 bd55df49...bc61aa): submit callback 0x381e72c -> helper 0x1cba62c -> vtable slot +0x98 (capability). `PluginWrapperElement` (vtable 0x7c36438) and `ProgramEditParameterElement` (0x7c65aa8) have +0x98 = 0x1cb7bc0 (returns false) and +0xa8 (string setter) = 0x1cb7bf0 (immediate return). Raw: plugin-element-vtables.txt, setter-disassembly.txt, verification.txt (PASS from verify_contract.py). Offline structural check only.
- Limits: (a) XL 3.10.1.12 only; Key 61 binary not inspected, no on-device TextEditOverlay run ever done (docs say so); (b) only these two element types were inspected, so "other element kinds with a true +0x98" is open (but a Local/ or Fixed/ element would hold the text inside the UI, never reach the plugin); (c) the agy report's wording "the host binary gate drops it" is accurate for the call path (overlay closes, no write), but the report itself did no new analysis, it repeats native-text-entry.md.
- Verdict: for a normal Parameter N handle the claim is a FACT for XL 3.10.1.12 (disassembly) plus a doc statement (6.12); for Key 61 it is an unverified extrapolation (same code base, 3.10.1.x). Reasonable to treat as true, cheap to confirm with probe A below.

## 3. Any documented/observed way a third-party plugin receives host-typed text?
- effString2Parameter: NOT called (SDK host-contract.md:58). Fact.
- effSetProgramName: framework ignores it (mpc_plugin.h:662 `return 0`); host-contract.md says the host only enumerates names (effGetProgramNameIndexed) and "program number is saved". No document or observation shows the host's preset/program rename flow calling effSetProgramName on a plugin; host-side preset names live in the host's own files. HYPOTHESIS/unsupported either way. (native-text-entry.md also rules out program-name hijacking as a substitute.)
- audioMasterUpdateDisplay / getParameterDisplay: plugin->host direction only (names/values re-read; host-contract.md:58). Our code already uses it (synthyboy_mpc.cpp:3006-3009, macro names as Q proxy names, macro_names.h:55).
- Chunk: host-opaque, plugin->host->plugin round trip of saved state only, no user text.
- Conclusion: no documented text-return channel. The only plugin-received data from the screen are parameter values (floats).

## 4. Alternative: native on-screen keyboard from skin Buttons (RECOMMENDED)
Data path: Button tap -> `Parameter K` float (buttonId step) -> setParameter on the plugin -> plugin keeps the string -> display string of a text parameter -> Label (type Value) -> OK sends the string to the owner (macro/LFO).

SDK constructs (all official, ui-reference.md):
- Radio button group, 6.4 (line 939-981): N buttons bound to the same handle, `buttonId` 0..N-1, `numButtonsInGroup` N; a press sets the value to step `buttonId` (quantised to max(N,2) steps, normalised id/(N-1)). Images only (no text on a Button): glyph artwork is a PNG per key (filmstrip not needed, each key own on/off image), size of the entry = image size.
- Momentary press: modifier `ResetOnGestureEnd/Parameter N` (7.2 line ~1510) "returns to the default value when the finger lifts". Default is 0 (UI reset uses 0, host-contract.md:62). So key id 0 = idle, characters 1..; the host itself sends k then 0, repeated identical characters work without a plugin round trip. The plugin latches on setParameter edge (value != 0) into a lock-free ring; it must not rely on getParameter polling.
- Label type `Value` (6.3 line 878-937, "Value its display string") bound to `Parameter M`: shows what effGetParamDisplay returns. Dynamic strings via effGetParamDisplay are already used by this plugin: synthyboy_mpc.cpp:4455 (FX band choice), :4461 (Scale Root "Select root"/"Play"), 4416.
- Layers without plugin help: `Local/<range>/<id>` UI-only handle (7.3 line 1518) + `IndexedEnabling/<i>/<n>/Local/3/layer` in `additionalInvalidatingHandles` of the key group bounds (7.4). Three overlapped key sets (lower, UPPER, 123/symbols), each key own buttonId, so the plugin never needs to know the shift state. Layer switch = a 3-button radio on `Local/3/layer`. Shift-once auto-release is not possible with Local (UI-only); caps-lock style is.
- Open/close: a context parameter written by the host (card "rename" button = radio group id 1..8 macro, 9 save-as, 10 rename) and rewritten by the plugin when done (audioMasterAutomate). The keyboard panel's bounds use `additionalInvalidatingHandles: ["NonZero/Parameter C"]` (7.2 `NonZero`) so it shows only while ctx != 0 (7.4 conditional visibility). The plugin sets the initial text and title when ctx opens, rejecting stale contexts (ctx change while open = new session).
- replacementStrings (3.3): not needed for text; useful for `Parameter C` only as fixed step labels. Dynamic title = the display string of `Parameter C` (changes per ctx), like Scale Root input.

Parameters (append to `nativeui`, 3 parameters, no count problem: it adds 3 to nativeui::kCount):
| name | range | writer | notes |
|---|---|---|---|
| `TextEdit Context` | 0..10 (11 steps: 0 closed, 1-8 macro 1-8, 9 shape save-as, 10 shape rename) | host (open) / plugin (close) | display string = title ("NAME MACRO 3" / "NAME OF THE SHAPE"), <=31 bytes |
| `TextEdit Key` | 0..99 (100 steps: 0 idle, 1..95 = ASCII 32..126 minus 31, 96 backspace, 97 clear, 98 OK, 99 cancel) with `ResetOnGestureEnd` | host | ring buffer in setParameter; value reported back is always 0 |
| `TextEdit Text` | 0..1023 counter (1024 steps) | plugin only | display string = current text + caret, 31 bytes; counter increments each edit so the host redraws; read-only (Label only, acceptsHWFocus No) |
Limits found: display/name buffer is 31 chars + NUL (host_strings.h:24, `kParamStrBytes`=32, the host buffer size is unmeasured). Macro names are max 16 chars (content_state.h:37) so they fit; LFO shape names are max 40 (lfo_ui.h:3665) and DO NOT fit in 31 bytes: show the tail ("..." + last 28 chars) or limit the native keyboard name to 28-30 chars, or split across 2 Text parameters (2 Labels side by side/two rows). UTF-8: non-ASCII keys are not in the table above; owner decides if accents are required (more ids, N larger; steps up to a few hundred are within float precision).

Risks (all HYPOTHESES until probed; none of these constructs is used anywhere in the repo yet: `ResetOnGestureEnd` and `Local/` have zero hits in scripts/, shell-mpc/ and docs/):
1. `ResetOnGestureEnd` on a Button may not send both k and 0 setParameter calls (or may coalesce them). Fallback: plugin resets to 0 itself with audioMasterAutomate after consuming (a quick double tap of the same key could then lose a character) or alternate two key params (even/odd) so the value always changes.
2. The Label may not re-read the display string on audioMasterAutomate when the text parameter value changes (our Scale Root Input does change its string with a value change, but via the same path with a value flip; for the counter this is untested). Fallback: audioMasterUpdateDisplay (documented: re-read names/value texts, but also rebuilds the plugin UI page = flicker, "use sparingly", and a measured Key 61 reaction in docs/MPC.md "Q proxies").
3. Label display string length (31 bytes) vs 40-char shape names; host buffer size unmeasured.
4. Radio group of 100 Buttons: host quantisation/rounding of id/(N-1); 100+ widgets per layer x 3 layers (~300 widgets) may hit layout/paint cost on the Key 61 (see docs/dsp-knowledge/mpc-display.md and measurement.md on widget costs; the Voice page already measured 207 notifications on LFO live params).
5. `Local/` handle in a Button group and in `IndexedEnabling` for visibility: documented in 7.3, "well-trodden" status not claimed; untested here.
6. Text from MIDI/automation: `TextEdit Key` is automatable by default; return false in effCanBeAutomated (also for ctx and text) so no lane records them.
7. Project save/restore: these params must not be saved (reset to idle/closed on load; a restore with ctx != 0 would open the keyboard).

## 5. Minimal probe on the Key 61 (first, before any product code)
Goal: prove (a) host TextEditOverlay on a plain parameter drops text (Key 61), (b) key Button with ResetOnGestureEnd produces k,0 sequence, (c) text Label updates through audioMasterAutomate.
Test plugin = the SDK example (`/Users/szabi/.local/share/local-worker/ext/mpc-sdk/examples/DrumSynth`) or a throw-away copy of our shell, armv7 build only (Key 61), installed as a separate folder (own uid/name) so the working package stays; no changes to the shipped package.
Probe skin `TUI.json` (one tab, 1280x800 coordinates per 1.4):
 1. Plugin params: P0 "Ctx"(11 steps), P1 "Key" (100 steps), P2 "Text" (1024 steps), P3 "Num" plain float, P4 "Echo" (to display a log string of the last 8 raw values received).
 2. Page: a Label Value on P2; a Label Value on P4; 4 key Buttons (A,B,C,Backspace) in a radio group on `ResetOnGestureEnd/Parameter 1` with numButtonsInGroup 100, ids 1,2,3,96; a 3-button layer radio on `Local/3/layer` with two overlapped sets (A,B,C vs a,b,c) switched by `IndexedEnabling`; a Button on P0 id 1 opening a panel shown by `NonZero/Parameter 0`; plus a TextEditOverlay bound to `Parameter 3` and opened like the factory (`Show Overlay`, additionalData `text edit overlay`, SDK 6.9-6.12) as probe A.
 3. Plugin: in setParameter log every call to a file under /tmp-like plugin data dir (index, raw value, timestamp, thread) and append to the P2 text; on a timer (display thread) call audioMasterAutomate for P2 with the new counter; run variant 2 with audioMasterUpdateDisplay.
Steps and readouts: (i) tap A twice quickly, tap B, backspace; read the log: expect 1,0,1,0,2,0,96,0 (accept: a 0 after every key). (ii) check P2 Label shows "AAB" -> "AA" within <200 ms and note the display-string latency. (iii) layer switch: lower/upper sets send different ids; Local layer works with IndexedEnabling. (iv) probe A: double-tap the Num control, type on the factory keyboard, press Enter; log must show NO setParameter on P3 / no effString2Parameter (opcode 27 counter in the dispatcher). (v) record 15 s of host CPU (top) with the keyboard panel visible (~100 widgets) for risk 4. Save raw logs and package hash under `.hw-local/mpc-perf/` (shared dir) per AGENTS.md.
Disproves/changes the plan: no `0` after k (fallback to reset-from-plugin / alternating params); the Label not refreshing on automate (UpdateDisplay variant); widget cost too high (reduce keys: one layer + a symbol set on demand using visibility).

## Summary of verdict
- Claim "host drops text for third-party VST" = FACT for XL 3.10.1.12 (disassembly of 2 element types + SDK 6.12 doc), unverified on Key 61 (no binary, no device test). It does not cover a native Button keyboard.
- There is no documented text-return channel (string2parameter is never called; setProgramName unverified/ignored by the framework).
- A native Button keyboard is feasible with documented constructs and 3 parameters, with several unproven host behaviours (ResetOnGestureEnd on Buttons, Label refresh, Local/IndexedEnabling for layers) that one 1-hour Key 61 probe settles.
