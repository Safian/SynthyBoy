## 0. Verdict

YES, the skin can put one static full-tab image per tab under all widgets, and our repo already does it once (Play tab). The mechanism that fits is an `Image` (Regular) as the FIRST `componentsData` entry of the tab, gated by `RangedEnabling` on "Overlay Instance" so it is visible only while our page is up (frame 24), exactly the pattern of the existing LFO shape picture. The tab-root `backgroundData.image` is NOT suitable (cannot be gated, see 1.3). Open points that only a device can settle: pixel exactness at 1:1, decode cost per image, whether the host's Q-Link highlight must be suppressed, switch-over flash (section 8).

### 1.3 Why an Image widget and not `backgroundData.image`

`backgroundData` of the tab root cannot be gated by a handle; the fallback (overlay off or disabled, native widgets visible: `83_pages.py:5`) would then show native knobs over pre-rendered knob surrounds. The `Image` entry can be gated like the widgets. Scaling of `backgroundData.image`: NOT FOUND. Also `scripts/render-mpc-skin-preview.py:131` ignores `backgroundData.image` (paints a flat colour) but draws `Image` entries (`:110`), another reason for the Image entry.

## 4. Interplay with the overlay (question 4)

### 4.1 Markers (the page detection)
- The markers are SKIN widgets: 6 x 6 opaque RGB PNGs `Image` entries at tab `33 24`, `1241 24`, and the instance picture at `45 24` (ov43 `TUI.json`, tab `Macros`: `Overlay Marker macros left`, `... right`, `Overlay Instance macros`; colours `6b3a2c`/`3a6b64` for macros: `overlay_layout.json`, view `macros`). Detector: reads the primary framebuffer 10 times a second, both markers must match within 2 per channel at four corner samples and the centre (`docs/MPC.md:852`; status line `markers_read_<view>: left=.. right=.. (expected ..)`: `shell-mpc/overlay/controller.h:1569`).
- A background Image at index 0 lies BELOW them (paint order, `ui-reference.md:486`), the markers are separate opaque widgets: the background cannot change their pixels. The marker detection does not break by this.
- BUT today the overlay's opaque picture paints the three squares over with the cover colour `1e1d1e` (`docs/MPC.md:852`: "the overlay's picture covers them ... so the player never sees them"). With a transparent plane the squares would be VISIBLE to the player. Required: the plane keeps three small opaque cover patches (precedent: "the transparent envelope view paints only its two squares", `docs/MPC.md:834`, measured on both devices), and the background must be flat-coloured where the patches lie (x 33-39, 45-51, 1241-1247; y 24-30 in tab coordinates), or the patch must carry the background's pixels. The cover colour `1e1d1e` does not equal the gradient everywhere (gradient `bg0`..`bg1`): the generator must emit a flat-ground rectangle there, or the patch colour must be read from the same function.
- Standby dim and the rotation search read the same marker pixels (`docs/MPC.md:842,897-901`): unaffected by what is under the markers.

### 4.2 The keyed Q-Link panel and the host's own Q-Link highlight
- The panel key compares a 16 x 220 grid of the strip x 840..1280 with a reference taken when the page is settled (`docs/MPC.md:1175`: "The host picture under our page is static (the skin's hidden widgets), so it is taken as a reference"). With the background in the host plane the strip stays static (host-drawn), so the reference still works and gets MORE texture; the first column where most rows differ is the pop-up's edge (tolerance 3 levels). The clip (`panelEdgeX`) is still needed for our LIVE ops (they lie on a plane ABOVE the host's pop-up), but the static content is covered by the pop-up automatically. The `PanelKey` tests (`panel_key_host`, `qlink_panel_host`) need a case with a textured reference.
- DONE (2026-11-21, work/qlink-bounds): `qlinkBoundsData: []` on all tabs of the overlay skin (`97_no_fallback.py`); the owner's XL photo showed stray host badges 3 / 7 / 4 / 8 inside the Env / LFO graphs with the old frames kept. `hideQLinkBounds` (component version 4) is not needed and stays untested. Verification on a device: TODO.md.
- Risk found (now handled, see the line above): the host draws its Q-Link group highlight rectangles from `qlinkBoundsData` (`ui-reference.md:426-441`; ours `90_frames.py`, e.g. Macros `["16 301 288 323", ...]`) on its plane. Today our opaque plane hides them; with a transparent plane they show through next to our own yellow frame. Options: `qlinkBoundsData: []` on the overlay-variant tabs (loses the highlight in the fallback), or a custom component version 4 with `hideQLinkBounds` wrapping the gated background (suppression "while this component is shown": would exactly follow the gate; untested, NOT FOUND whether it works for a nested component).

### 4.3 Switch-over
The host shows the background only after it has redrawn the tab with frame 24 (needs the plugin's `audioMasterAutomate` report; the same latency as the widget hiding today, `docs/MPC.md:1173`, `instance_slots.h:28`). Until then the native widgets (frame 0..18) are visible. So the overlay must stay OPAQUE until it has verified that the host drew the background (a sentinel pixel of the background read from the primary framebuffer exactly like the markers: this also proves 1:1 and the colour pipeline), and only then go transparent over the static areas. The reverse (page closes) must make the plane opaque or off in the same tick that the frame leaves 24.

## 5. Risks

1. Pixel exactness: "scaled to the entry bounds" with equal size and a 90 degree panel rotation (`docs/MPC.md:143`: UI pixel (X, Y) at panel (Y, 1279 - X)); resampling of text edges NOT FOUND. Sentinel + a screenshot compare answer it.
2. Memory cost of a plain image (decode, tmpfs, per track, eager) NOT FOUND; 70 MB estimate vs 422 MB unexplained host figure.
3. Skin load time grows (22 PNG decodes of 3.2 MB); the host has "unpack" behaviour (`MPC.md:117`); `docs/MPC.md:1383-1470` (start-up time) must be re-measured.
4. Host Q-Link highlight shows through a transparent plane (4.2).
5. The three marker cover patches must match the host background (4.1); a gradient makes flat patches necessary.
6. Switch-over flash of native widgets (4.3); stale frame values (`docs/MPC.md:852`: a host "shows a stale frame until the parameter is reported").
7. The static set is not yet defined: cells are cache units, not static/live; a baked pixel that later changes (a value, a name, a chip, a lit LED) would remain in the host picture and cannot be erased (our plane can only add on top; to hide a baked pixel the plane must paint an opaque patch). Two-state elements: rest state in the background, ACTIVE state on top (owner decision, `overlay-static-anim-layers.md:178`). Element look that differs between states in a way that is not "add on top" (e.g. inactive grey look: `Pen::inactiveGrey`, `docs/MPC.md:1139`-area) needs an opaque patch.
8. Fallback must not change: with the overlay off or disabled the production behaviour stays (the gate makes the background invisible; `scripts/tests/test_mpc_skin_overlay.py` must still compare the production skin byte for byte).
9. Key 61 vs XL: plane format/alpha blend of a mostly transparent ARGB plane over the host plane is proven by the Env view (`MPC.md:834`) but not for a full-page one; also "cheaper" is unmeasured (the saving is in our GPU/CPU drawing, not in the display controller).
10. Two plans must not run in parallel: `overlay-static-anim-layers.md` (helper-internal static layer; its T-bg baked-file task) and this one change the same drawing files; this plan's backgrounds make the helper-side static layer for the covered content unnecessary.
11. The three-slot test project problem: an old project keeps the old Q-Link snapshot per track (`docs/MPC.md:1177`), so test in a NEW project.
