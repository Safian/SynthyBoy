## 1. GPU helper restart after a preset change (XL, Reverse Gong Swell -> Spectral Chord Morph)

Raised in `shell-mpc/overlay/gpu/gpu_overlay.h:197-198` (`GpuHelperBackend::poll`): `unacked_ && now - unackedSince_ > cfg_.ackTimeoutMs` (`ackTimeoutMs` 700, line 117) -> `fail()` -> restart after back-off (1 s, `restarts` 1, new pid). Verdict of the restart machinery: working as designed (restart 1 of 3, back to `running`).

How it is measured: `now` is `steady_clock` milliseconds since the service epoch, taken ONCE at the start of an overlay tick (`service.h` run loop, `now` before `controller_->tick (now)`). `submit()` (line ~235) sets `unackedSince_ = now` when a scene is handed over while none is unacknowledged; a `kMsgFrame` from the helper with `seq >= lastSeq_` clears it, an older ack moves the timer forward (progress). `poll()` reads all pending helper messages BEFORE it checks the timeout (lines 163-174 then 197), so a stalled overlay thread cannot cause a false timeout by itself: an ack that is already in the socket clears the flag first. A heavy `effSetChunk` / `effSetProgram` on the host thread does not block the sender either: `applyState` (`synthyboy_mpc.cpp:1879`) holds `contentMutex`, and the controller takes its own `mu_`, a different lock; the acknowledgement is sent by the helper PROCESS (`gpu-helper/main.cpp:1888`), not by a thread of the plugin. So "acknowledgement from a thread a preset change blocks" is excluded.

What the helper does between pictures: `loop()` (`main.cpp:2072`) sleeps in `poll()` up to the pacer's slot, reads messages, and only draws when a scene is `dirty_`; a scene of another region size (`s.w != w_`, line 1758-1759) returns false and is retried every 5 ms with NO acknowledgement until the right scene arrives; `onShow` recreates the surface (`createSurface`, `dirty_ = false`) and the first picture after it also builds the cell layers. All of that sits inside the 700 ms window that starts at `submit()`.

What can delay the acknowledgement past 700 ms (most likely first): (a) the helper process starved of CPU while the engine builds the content of a heavy preset (Spectral Chord Morph and Spectral Gong Pad carry `samples` in their content; the build runs on the host/engine threads, helper and engine share cores 0-3 at nice 0, `service.h` header); (b) a hide -> show cycle around the host list (the list pop-up hides the view: `hide()`, then `show()` + first scene after `Hidden`): surface re-creation plus first full layer render under that CPU load is inside the same 700 ms; (c) the overlay thread stalled in a display call so that `now` is older than the real time of the submit (the window shrinks by the stall; the step's `now` is not refreshed before `submit`).

Verdict: a legitimate restart whose trigger is not proven. Not a defect in the acknowledgement path (no blocked sender), but the ack window is the same 700 ms for a steady frame and for the first picture after a `show` (surface creation + layers), which is a plausible margin problem on the XL under load. NOT fixed: there is no saved status/log of that moment (no file in the evidence folders holds `22717`/`9980` for the XL; `xl-ov9/fault_log.txt` shows the same error earlier, at an injected hang). Needed to close it: the status file `gpu_*` lines around the selection (`render_ms`, `setplane_ms` of the last frame before the failure, `gpu_last_error`), and the time of the first frame after the preceding `show` (`helper_render_ms` max). If the first frame after a show exceeds about 400 ms under load, the fix is a longer ack window for the first scene after a `show` (a `GpuConfig` value, tested in `shell-mpc/overlay/tests/gpu_backend_host.cpp` with the fake helper that withholds the frame). Device check: select Spectral Chord Morph from the host list ten times in a row with the play log off and the status file on (`touch /tmp/synthyboy-overlay-status-on`); `gpu_helper_restarts` must stay 0.

## 2. Trailing `*` after the program name

**Resolved (owner decision, 2026-11-19): the mark is gone by design.** The plugin no longer appends `" *"` to any name (`programModified` / `setProgramModified` removed; see `docs/MPC.md` "Q proxies"); a project saved with "Name *" loads as "Name". The analysis below describes the removed behaviour and is kept as history; its line numbers refer to the code before the removal.

The star is NOT the host's compare: the plugin writes it itself. `synthyboy_mpc.cpp:2143-2145` (`effGetProgramName`) appends `" *"` while `programModified` is set; `setProgramModified (true)` is called from only two places: `effSetChunk` (line 2533, "a project's state") and `writeRealParam` (line 2862) when a host / Q / UI write CHANGES the parameter mirror; `effSetProgram` clears it (line 2115) except in the `wasProtected` early return (line 2095-2100, the saved program re-selected after a chunk restore), which leaves the flag as it was. The host drops the mark only when told (`audioMasterUpdateDisplay`, `programMarkDue`).

So a preset shows `*` only if, after `effSetProgram`, something writes a real parameter to a different value (or the host sends a chunk). The tempting cause, a value that does not survive the host's normalised read/write round trip, was tested: `core` + `loadPreset` of all 160 factory presets, each parameter through `toNormalised` -> `fromNormalised` -> `constrainValue` (what `writeRealParam` does with a host write-back). Result: ALL 160 presets contain 136 to 162 parameters that do not come back bit-exact (examples: `env1.decay_curve -3 -> -2.99999952`, `filter1.cutoff 2600 -> 2599.99976`, `osc1.unison.detune_curve 1.5 -> 1.49999976`; the eight starred ones have 139 to 151, no parameter is typical of them). Since 152 of 160 presets do not get the star, the host does not write back every parameter after a program load; the star appears only when the host (or the plugin's own Q / Play echo path) writes one of the parameters. That is a real fragility but it is not the discriminator.

What is certain: `writeRealParam` accepts an exact echo of what the plugin itself reported (`toNormalised (mirror)`) as a change when the float round trip is off by an ulp (only the Q router, the Play proxies and the restore window have echo tolerance, 1e-6). What is not shown: which write follows the load for those eight presets. Their common trait in the files: every preset has `macro_names`; Spectral Chord Morph and Spectral Gong Pad also have `samples`; nothing else separates them (checked: format 1, state version 4 for all). NOT fixed (cause not certain; a blanket "ignore a write equal to the reported normalised value" would be a safe hardening but cannot be shown to remove these stars). Needed: with the debug log on (`touch /tmp/synthyboy-play-log`, `docs/MPC.md` "Debug log"), select Space Wobble Bass from the host list and read `/tmp/synthyboy-play-log.txt`: the lines after `effSetProgram` show every `setParameter` (index, value, "written"/"echo") and any `effSetChunk`; the first "written" line is the cause. The chunk compare asked for (apply preset -> `effGetChunk` vs the program's chunk) needs the plugin library, which needs the MPC SDK (`MPC_SDK`, not available here); `dump_chunks_host` / `programs_host` were not run.

## 3. Q group after a host dialog (Key 61)

By design Q events reach the router while the view is hidden: `QRouter::hostWrite` lives in the plugin (`setParameter`), independent of whether the overlay shows a page; the router keeps the group the last page published (`q_publish.h` `QSlots`: published once, again only when the slots change or after `forget()`). That is wanted: the knobs keep working on the last mapped group while a host dialog covers the page.

Evidence (`k61-shots/cap/r12m-118..120`): `play_highlight: 2` (ENV) before the dialog; during it `state: hidden: no view on screen`; after Cancel `play_highlight: 3` (LFO) and `touch_events` 24 -> 26. The frame (`PlayView::highlight_`, `play_view.h`) only changes in `PlayView::onTouch` (line 224: a Down with `x >= 850` and `y >= kTabY` selects the LFO third), so a Down event was delivered to the page by `Controller::touchEvent` (`controller.h:234`) in the step in which the page became visible again: the Cancel tap of the dialog sits in that area. The group the router had (ENV, from the last publish) is then replaced by the LFO group at the next `update()` (`publishQ`, `QSlots::publishRaw` compares with the last published slots), which is why the first Q1 turn after closing went to LFO: at return the frame and the router agree. So after the dialog closes the rule holds; the defect is that a tap that belongs to the HOST dialog moved the highlight.

Why the Down reached the page is not shown: `readTouch` / `deliverTouch` keep events of a hidden page as the host's (`noteHostTouch`), and a finger that went down on the host stays the host's until Up. A Down delivered anyway means the page check classified the step as visible before the dialog had gone from the markers, or the dialog closes on touch-down. Also noted: `shownView_` is not reset when the view only hides (`controller.h:540-547` sets `current_ = -1` but keeps `shownView_`), so `onShown()` (which forgets and re-publishes the Q group) does not run for the same view coming back; that is harmless today because `QSlots::publishRaw` re-publishes whenever the targets differ, but it means nothing re-asserts the router group after a hide if the instance's router was changed by another path meanwhile. NOT fixed: a time window that drops the first Down after a return would be a guess. Needed: a device run that logs `hostGesture_`, `touchEligible()` and the Down's coordinates at the Cancel tap (the status file counts `touch_events`, `touch_taken`; `touch_taken` unchanged between 119 and 120 would show the page did not take it, then the highlight comes from `onTouch` returning false after having set `highlight_`: line 224 sets it before it knows whether any control takes the touch). That last point IS visible in the code: `highlight_` changes on any Down in the lower area even when nothing under it is a control of the page; the test to write is "a Down delivered while the stack is main and no control is hit does not change the highlight" once the owner confirms that rule.

## 4. Release build status file (fixed: document)

Where: `controller.h:1495-1497` (`writeStatus`) and `1218-1219` (`readSwitches`); the option is `SYNTHYBOY_MPC_WRITE_FILES` (`write_files.h`), set to 0 by CMake when `SYNTHYBOY_MPC_DEV_LOG` is OFF (`shell-mpc/CMakeLists.txt:143-145`), which `scripts/build-mpc.sh --release` passes (line 92). With 0 the periodic status file is NOT written unless `/tmp/synthyboy-overlay-status-on` exists. The same option removes the profile report (`device_profile.h:295`), the PollGuard report (`poll_guard.h:59`), the helper's EGL probe (`gpu-helper/main.cpp:1972`) and the helper's log (`helper_transport_linux.h:39`). The code agrees with the owner's rule (no log files in the release package); what was wrong is the document: `docs/MPC.md` titled the table of files "Release build ... as built today (`SYNTHYBOY_MPC_DEV_LOG` ON)" and listed the status file as written once a second, which is the default (measuring) package, not `--release`.

Fix: `docs/MPC.md` now (a) names that table "Default package build", (b) marks the status-file bullet of the overlay section as "not in the release package, only on request", (c) has a new section "What a release package writes" (nothing periodic; status only on request through `/tmp/synthyboy-overlay-status-on`; the two state files `-gpu-minfreq.orig` and `-zpos-rest` may exist while their state is held; the switch files that are only read). Device check: run the release package, `ls /tmp/synthyboy-*` must show no status, profile, egl, gpu.log; then `touch /tmp/synthyboy-overlay-status-on` and the status file must appear within about 2 s.
