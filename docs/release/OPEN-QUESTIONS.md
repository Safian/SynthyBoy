- **[docs/MPC.md:597](docs/MPC.md#L597)**: - **Stacking against the host's pointer (the zpos rule, `discovery.h` `chooseZpos`, `shell-mpc/overlay/stacking.h`).** The host keeps its mouse pointer on a small plane of its own. Measured on the MPC XL (2026-11-16): planes 34 (the host's picture, zpos 0), 40 (the host's pointer, 64x64, type Overlay, zpos 1) and 46 (ours, zpos 2); every plane has a `zpos` property that is a MUTABLE range 0 .. 7; with ours at 2 the pointer was hidden UNDER our picture; after setting our plane's zpos to 0 the kernel's normalised order was host 0, ours 1, pointer 2 (planes with equal zpos are ordered by plane object id, the lower id below) and the pointer was visible on top, the overlay kept working. On the Key 61 no plane has a `zpos` property and the pointer is on top by the hardware's own order (measured). The rule: when the driver has a MUTABLE `zpos` on our plane, the value is the LOWEST that puts our plane directly above the application's primary plane and below every other plane the application has on the CRTC (its pointer and sprite planes), by the kernel's order (zpos, then plane id): the XL table gives 0; a plane whose id is lower than the primary's needs the primary's zpos + 1, and none is possible when that is not below the others, when the range does not allow it, when the property is immutable (or missing: the Key 61), or when the primary plane or the order of another plane is unknown; then today's behaviour stays (above every application plane, as the discovery chose it). The lowest value is chosen even when the plane's own would do, because the pointer plane may be hidden at that moment (a plane with no framebuffer is not on the CRTC and is not in the list) and come later at a low zpos. The set is the property call `DRM_IOCTL_MODE_OBJ_SETPROPERTY` through the application's descriptor (the master), the values are read through our own; it is made ONCE when the plane is taken (CPU path: before the first `SETPLANE` of a shown picture; GPU path: before the helper is started), again whenever the plane is taken again after a loss (another plane after `nextPlane`, a helper restart) and when the plane was found switched off by a mode set of the application and is set again (CPU path: `planeWasSwitchedOff`; GPU path: the helper counts it in `PaceBlock::planeRefreshes` and the plugin takes the stacking again), because a mode set may have reset the property with the plane. The zpos the plane had at rest is remembered when the plugin first touches it and written back when the overlay releases the plane (the picture is hidden: `disablePlane`; the helper stopped, failed, or was told to quit: `cleanDisplay` -> `releaseStacking`; the plugin took the plane away after a helper failure), but NOT on a plane that was lost to another program (`abandonPlane`, a `SETPLANE` error of the helper on a plane that is not free): that plane is not ours to write to. A failing set or restore is not fatal: it is counted and written to the status text, the plane stays as it is. A crash of the whole application leaves the changed zpos on the plane until the next start (the next start reads it as its rest value; the rule gives the same target). **Not verified on a device:** the XL (the only device with a mutable `zpos`) was not available to this work; the rule and the guard are tested with the XL's table and a fake driver (`stacking_host`, `gpu_backend_host`), the Key 61 run shows the no-property path. Status file: `display_plane_zpos` (`rest 2, set 0`; `none (the plane has no zpos property)`; `unchanged (...)` with the reason; `set failed: ...`; `(restored)` after the release), `display_pointer_plane` (`above ours` = the pointer is visible, `covered by ours`, `none`, `unknown (no zpos on every plane)`), `display_plane_zpos_counts`.

- **[docs/MPC.md:904](docs/MPC.md#L904)**: **The flicker with the pop-up (reported by the owner on 2026-11-16, package `ov25-all-ui`; cause found and fixed in the code the same day, host tests only).** The report: on the MPC Key 61 the UI flickered while a Q-Link knob was turned; with the pop-up ON and turning, it looked right for a while, then the right strip flickered EMPTY (our picture cut away, the host's empty background showing) and stayed so until the tab was changed (Play -> Macros -> Play), which takes the key's reference again. With it off no panel comes up over the plugin's pages. **The plugin reads the option** (`qlink_setting.h`, read only, the file is never written): when the overlay starts and again whenever the file's modification time or size changes (one `stat` a second; the file, about 77 KB, is read only then).
