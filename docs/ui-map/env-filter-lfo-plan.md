## 0. Four facts the plan rests on (they correct the brief)

1. **The Note / Velocity curves are CONTENT, not parameters.** `docs/params.json` has exactly two `curve.*` keys: `curve.velocity.legato` and `curve.note.legato` (stepped 0 / 1, "Off" / "On", automatable, not modulatable, default 0). The curve points are `StateContent::velocityCurve` / `noteCurve` (`core/include/synthyboy/content_state.h:155`): `std::vector<ContentPoint>` (x, y, power; `power` = the bend of the segment after the point, same as LFO shape points), empty = identity, otherwise 2 .. `kMaxCurvePoints` = 64 points with ascending x in 0..1. The engine bakes them with `shapes::ShapeData` (`own_content.h:85-101`, `sanitize()`, `bake()`) and reads the sources `velocity` (choice 23) / `note` (choice 24) through them (`voice.cpp:808-822`, `curvedSource`, `voice.cpp:212`); with legato On a change after a legato note-on glides with the time constant `master.portamento.time`. The Serum import fills the same fields (`serum_fx.cpp:1070-1095`). So the new editors write CONTENT (like the LFO shape editor) plus the two legato keys.
2. **The desktop reference is a stub.** `ModVelNotePanel.cpp` keeps five points in a local vector (`resetPoints()`), never stores them (the panel itself shows a GAP badge "custom multi-point curve storage is an engine GAP") and has only the two legato keys + `master.velocity_track` as controls. It is a behaviour reference only for the drag rules (end points fixed at x 0 and 1, a middle point moves between its neighbours, y 0..1) and the axis labels (NOTE: C-1 (0), C1 (36), C3 (60), C5 (84), G9 (127); VELO: 0, 32, 64, 96, 127), NOT for storage. Real reference for storage and behaviour: the engine (above) and the MPC LFO shape editor (`shell-mpc/ui/shape_editor.h`, `lfo_ui.h` `flushShape`, `IInstanceView::setLfoShape`).
3. **A plugin-drawn page cannot change the host's tab today.** The host owns the function keys / tabs; the overlay's touch reader opens the touch node read only and never grabs it (`touch_linux.h:214, 425`), `kit/` and `overlay/` have no navigation call, and `docs/release/DEVICE-CHECKLIST.md:86` lists "trigger host page or tab changes via VST2 audioMaster opcodes" as `[OPEN]`. Section (e) therefore has a blocking UNVERIFIED part.
4. **Marker colours and instance slots do not depend on the tab list.** The instance slots (16 colours, `instance_slots.h`, `overlay_layout.json` "instance") belong to plugin instances, not pages. Each view has its own marker colour pair; removing 7 views frees 7 pairs and leaves the other 15 untouched if the kept views keep their colours (recommended).

## (b) The selector component ("used + one free")

**Component** `ui::UsedSelector` (`shell-mpc/ui/used_selector.h`, library style: `Component`, `Change{id, kind, value}`, no parameter knowledge). Input per update: `items[]` = every candidate {number, label, `used`}, `selected`. It shows: every item with `used` or `== selected`, in number order (LFO 1..10, then R1..R4; ENV 1..6), then ONE `+` cell if at least one candidate is neither used nor selected. Cell width 56 px, height 56 px like the cells today (`InstanceBar::kCellW`, `EnvSelector`); at most 6 cells (Env + `+`: 7) or 10 + 4 + `+` = 15 cells in the worst case: the cells shrink / the row scrolls horizontally with the existing carousel behaviour (UNVERIFIED which: `InstanceBar` today has 14 fixed cells in one bar; in the worst case 15 cells at 56 px = 840 px fits the 1280 px top bar next to CLOSE-less page mode and TARGETS: check at step 3).

**Data source per selector** (a helper in `ui_bind.h`, one scan of the 64 slots per refresh, done together with `refreshMods`, not per frame):
- `usedSources (IInstanceView&, bool used[kNumSources + 1])`: for `s` in 0..63, `sp = modSlotParams (s)`; `src = lround (param (sp.source))`; a slot counts when `src > 0` and `lround (param (sp.destination)) > 0` (the same rule as `slotsOfSource`); then `used[src]`, and `used[aux]` for `aux = lround (param (sp.auxSource)) > 0` of that slot (an aux of an empty slot does not count: `freeSlot` treats `source == 0` as free). Source ids (`core/src/modulation.cpp`): ENV n = n (1..6); LFO n = 6 + n (1..8), LFO 9 = 33, LFO 10 = 34; RND n = 14 + n (15..18); Velocity 23, Note 24 (`uibind::envSource`, `lfoSource`; add `rndSource`). A switched-off (`power` = 0) or bypassed slot still counts (it is assigned; UNVERIFIED: `modNN.power` semantics, check `mod_ui.h`).
- Env: items ENV 1..6; **ENV 1 is always shown** (the amplitude envelope, hard wired; an empty preset shows `1` and `+`). Empty preset: `[1] [+]`.
- LFO: items LFO 1..10, R1..R4. Empty preset: `[1] [+]`. LFO 7-10 appear after 6 is assigned simply because they are not used until then and `+` selects the first free one in number order (LFO 1..10 first; the R items are offered only through `+`, see below).
- Play page selectors: same component, same data, same rule, bound to the same selection state (below): `Play Env` and `Play LFO` rows of `play_view.h` use `UsedSelector` instead of the 6 / 14 fixed cells (the compact view's popup list `list_` of `env_ui.h:732-744` becomes the component's list). Where the Play page has less width (compact third), the selector is a stepper + the list popup showing ONLY the used + selected + `+` rows: consistent with the rule.

**`+` behaviour.** Env: a tap selects the next free ENV (lowest number not used, not selected); no parameter is written. LFO: a tap opens a two-row popup (`ListPopup`): "LFO n" (the lowest free standard LFO, if any) and "RND m" (the lowest free random LFO, if any); with only one row it selects at once. Choosing selects the item: it is now `selected`, so it is shown (counts as "being edited"); NOTHING is written to the engine until the user edits a control or assigns a target (`TARGETS` -> ADD TARGET writes the slot; then the item is `used`). When the user selects another item and the previous one is neither used nor edited, it disappears from the row (its parameters stay). Order is always by number, never by recency.

**Persistence (decision).** There is no engine or preset state for a selector; the existing pattern is the plugin's selector parameters "Play Osc", "Play Env", "Play LFO" (`play_params.h`: stepped, not automatable, saved in the chunk as `mpcPlayOsc5` / `mpcPlayEnv` / `mpcPlayLfo`, `IInstanceView::playSelection / setPlaySelection`, `playSetSelector`), and the chunk-only settings without a host parameter (`mpcOutputLimiter`, pad pressure: `chunkWithOutputLimiter`, `synthyboy_mpc.cpp:402, 1883`). Today a tab page keeps its own selection in memory (`pageSel_` of `env_ui.h:97, 912`; `lfoNum_` / `rnd_` of `lfo_ui.h:127`, "a random LFO is chosen here only"; `sel_` of `filter_ui.h:100`): it is lost on a reload and on every view rebuild. Decision:
- **Env: the selection IS `Play Env` (1..6)**, **LFO: `Play LFO` (1..10)** (existing, chunk-saved, host-visible, no new host parameter, the host parameter count and the skin's Q proxies stay as they are). The merged tab and the Play page share the selection (the tab no longer has "its own"; consistent with the owner's "same rule on the Play page"). The `setPlaySelection` call in `selectSlot` is no longer limited to `! page_`.
- **Random LFO and the Filter view** have no existing slot: new **chunk-only** view state `mpcTabView` = `{ rnd: 0..4 (0 = a standard LFO), filter: 0..3 (F1, F2, NOTE, VELO) }`, `IInstanceView::tabView (int what)` / `setTabView (int what, int value)` (default 0, an old chunk without it leaves the defaults), no host parameter, no engine parameter. `rnd != 0` means "the random LFO `rnd` is the LFO being edited" (Play LFO keeps its last standard number).
- **Program change / preset load vs project reload:** a project reload restores the chunk exactly (the saved selection, even an unused one, is shown as "being edited"); a program change to another preset keeps the selection if the item is used in the new preset, else snaps to the first used one (UNVERIFIED how `synthyboy_mpc.cpp` distinguishes a chunk restore from `effSetProgram`; check at step 1; if it cannot, the selection is simply kept and an unused one is shown as selected, which is harmless).
- Tests (host, no device): `ui_used_selector_host.cpp` (pure component: empty -> `[1][+]`; partly used {1,2,5} + selected 2 -> `[1][2][5][+]`; selected unused 7 -> `[1][2][5][7][+]`; all used -> no `+`; order; `+` result; LFO `+` popup rows incl. both exhausted), `lfo_ui_host.cpp` / `env_ui_host.cpp` (the list from a fake view with slots set: source, aux, bypassed, empty-slot aux not counted; LFO 7 appears after 6 is assigned; R1 appears when used or chosen; hidden LFO keeps its values after select-away and re-select), `play_restore_host.cpp` (chunk round trip of `Play Env`, `Play LFO`, `mpcTabView`; an old chunk), `qslots_host.cpp` (Q-Links follow the selected item), gallery states: empty, partly used (1, 2, 5 + `+`), all used.

## (d) The NOTE and VELO editors (new, Filter tab states 3 and 4)

**Parameters read / written (all of them).**
- Read: `content.velocityCurve` / `content.noteCurve` (`IInstanceView::content()`); `curve.velocity.legato` / `curve.note.legato` (0 / 1); `master.portamento.time` (read-only chip: the glide time of legato); the mod slots (`modNN.source`, `.destination`, `.amount`, `.bipolar`, `.bypass`, `.auxSource`) for the routing list.
- Written: the curve points through a NEW `IInstanceView::setScalarCurve (int which /*0 velocity, 1 note*/, const std::vector<synthyboy::ContentPoint>&)` (default no-op, like `setLfoShape`); in `synthyboy_mpc.cpp` a request / poll pair copied from `requestLfoShape` / `lfoShapePoll` (mutex, latest wins, display thread copies `content` under `contentMutex`, `validateContent`, `engine->setContent`; a curve the validation would refuse is not applied); the two legato keys through `writeParam`; slot edits only through the existing TARGETS page (depth, polarity, bypass, remove, ADD TARGET via `uibind::freeSlot`). Not written here: `master.velocity_track` (home: Master VOICE OPTS, one-home rule).
