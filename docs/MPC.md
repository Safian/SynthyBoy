# SynthyBoy MPC Build Guide

## Build

The MPC package holds two builds of the same VST2 module: a 32-bit ARMv7 hard-float build with NEON (`VST/synthyboy-arm32.so`, `file32`: the MPC Key 61 and the other 32-bit MPCs) and a 64-bit AArch64 build (`VST/synthyboy-arm64.so`, `file64`: the MPC XL and the other 64-bit MPCs). The MPC loads the one that matches its CPU. The build script is `scripts/build-mpc.sh`; the host needs Docker. The environment variable `MPC_SDK` must point at a checkout of the MPC plugin SDK (it is not part of this repository and must not be copied into it). The environment variable `MPC_BUILD_IMAGE` (or the older `ARMV7_IMAGE`) selects the Docker image (default: the pinned Debian 12 image in the script); an image that already has the cross toolchains installed is faster because the script skips the `apt-get install` step inside the container.

The exact command line is `scripts/build-mpc.sh [--arch arm32|arm64|all] [--out DIR] [--jobs N] [--build-dir DIR] [--skins DIR] [--bench] [--no-validate]`; `--arch` defaults to `all`. `scripts/build-armv7-mpc.sh` is a thin wrapper for `scripts/build-mpc.sh --arch arm32` (output in `build-armv7-mpc/`) that keeps the old calls working. The script does the following, step by step:

1. For each architecture it runs a `docker run` container (running `scripts/mpc-container-build.sh`) mounting the source tree read-only, the build tree of that architecture (`<build-dir>/arm32`, `<build-dir>/arm64`), the output directory, and the SDK.
2. Inside the container it installs missing packages (the cross compiler, the matching `binutils`, `cmake`, `file`, `git`, `ninja` or `make`).
3. It runs `cmake` with the toolchain file `cmake/toolchains/armv7-linux-gnueabihf.cmake` (`-march=armv7-a -mfpu=neon -mfloat-abi=hard`) or `cmake/toolchains/aarch64-linux-gnu.cmake` (`-march=armv8-a`), with `-DSYNTHYBOY_BUILD_PLUGIN=OFF`, `-DSYNTHYBOY_BUILD_TESTS=OFF`, `-DSYNTHYBOY_BUILD_MPC_SHELL=ON`, `-DSYNTHYBOY_WITH_VITAL=OFF`, and `-DSYNTHYBOY_SHELL_ENGINE=own`. The package is the own engine; Vital is not built.
4. It builds the `synthyboy_mpc` target.
5. It checks, with the same checks for both architectures, that the `.so` is an ELF file of the right class and machine (`file`; for arm32 also `readelf -A`: hard-float), that it needs only `libc`, `libm`, `libdl`, `libpthread`, and the dynamic loader (`ld-linux-armhf` / `ld-linux-aarch64`), that it references no GLIBC symbol version above 2.39 (the glibc of the MPC OS 3 firmware; Debian 12 has 2.36) and no dynamic `libstdc++`, and that `VSTPluginMain` is the only exported symbol (using `nm -D`).
6. It produces a stripped copy (`synthyboy_mpc.stripped.so`) for the package, checks it again (same checks, and the exports after strip); the unstripped module stays in the build tree for profiling.
7. On the host it assembles ONE plugin folder `Safian - VST - SynthyBoy` with `VST/synthyboy-arm32.so` and `VST/synthyboy-arm64.so` (the stripped copies of this run only; `VST/` is emptied first) and `Content/presets` (a copy of `content/presets`).
8. It generates the Plugin Skins from `scripts/mpc-ui-pages.json` (using `scripts/gen-mpc-ui.py` and the SDK's `tools/gen_ui.py`, then `scripts/apply-mpc-skin-extras.py`), unless `--skins DIR` is given.
9. It generates `plugin.json` and `version.xml` via `scripts/gen-mpc-manifest.py`.
10. It runs the SDK's `tools/validate.py` on the finished folder. With `--arch all` the validator must report no error. The validator's schema lists `file32` and `file64` as required, while the SDK's `plugin-folder-format.md` says a 32-bit MPC uses only `file32` and a 64-bit one only `file64`; a single-architecture build (`--arch arm32` or `--arch arm64`) accepts exactly the one finding about the key of the architecture that was not built and fails on any other error.

### MPC XL (64-bit, AArch64)

The MPC XL has four Cortex-A55 and four Cortex-A76 cores and runs only the 64-bit loader (`/lib/ld-linux-aarch64.so.1`, libstdc++ 6.0.32). The arm64 module is built with the Debian 12 `g++-aarch64-linux-gnu` (glibc 2.36, below the 2.39 limit of the SDK validator), `-march=armv8-a` (no newer architecture level, no `-mcpu=native`, so it runs on the A55 and the A76 cores), `-static-libstdc++ -static-libgcc` and hidden visibility, the same link options as the arm32 module. `scripts/build-mpc.sh --arch arm64` builds only this one (the folder then has `file64` only).

The NEON loops of the own engine (`core/engine-own/dsp/simd.h`, `SB_NEON`) are compiled on arm64 Linux as well as on arm32 (not on Apple's arm64: macOS and iOS keep the scalar code). Like on arm32 the translation units that use them are compiled with `fp-contract=off`, so the NEON code and the scalar code (`-DSB_NO_NEON`) give the same samples to the last bit: all 112 factory presets rendered at tier low with `synthyboy_preset_render` gave identical WAV files with NEON and with `SB_NO_NEON` on AArch64, and so the arm64 module sounds like the arm32 one. (The arm64 scalar code that was used before, with the compiler's fused multiply-add, differs from both in the last bits.)

`--bench` also builds `synthyboy_bench` and `synthyboy_noteon_bench` with the same toolchain (a separate CMake tree `<build-dir>/<arch>-bench` with `-DSYNTHYBOY_BUILD_TESTS=ON`, libstdc++ linked statically) and puts them into `<out>/bench-arm32/` and `<out>/bench-arm64/`, outside the plugin folder; see Benchmark switches for what they do on the device.

The module must be built with GCC, not with Zig: `--exclude-libs,ALL` is not understood by Zig's linker and a Zig-built module crashed at host exit on the device.

The native acceptance is `sh shell-mpc/accept.sh` with `MPC_SDK` set. It builds the module natively on the development machine, runs the SDK host simulator with tests, checks the parameter table against `docs/params.json`, verifies the exported symbols, tests the factory presets as programs, runs the stub host for state round-trips, and builds and runs with ThreadSanitizer to check for data races.

## Package layout

The output folder is named `Safian - VST - SynthyBoy` and contains:

- `plugin.json` — the MPC manifest with `file32` (`VST/synthyboy-arm32.so`) and `file64` (`VST/synthyboy-arm64.so`); a key is written only for a binary that exists.
- `version.xml` — the content version of the package (the root manifest version with a fourth part) and, when `Plugin Skins` is present, the `uiversion` of the skins.
- `VST/synthyboy-arm32.so` — the stripped 32-bit ARMv7 shared object that exports only `VSTPluginMain`.
- `VST/synthyboy-arm64.so` — the stripped 64-bit AArch64 shared object that exports only `VSTPluginMain`.
- `VST/synthyboy-overlay-gpu-arm32` / `VST/synthyboy-overlay-gpu-arm64` — only in a package built with the overlay (`SYNTHYBOY_MPC_OVERLAY`, see "Overlay (experimental)"): the executable of the GPU helper, stripped, next to the plugin binary of its architecture. It is not in `plugin.json` (the host never loads it; the plugin starts it). The production package has no such file.
- `Content/presets` — the factory presets from `content/presets`, shown as programs in the MPC's preset browser.
- `Plugin Skins` — the touch-screen UI and Q-Links knob mapping, generated from `scripts/mpc-ui-pages.json` via `scripts/gen-mpc-ui.py` and the SDK's `tools/gen_ui.py`.

The plugin finds its own folder by walking up from the binary's path (obtained via `dladdr` on `VSTPluginMain`) to the first directory that contains a file named `plugin.json`. This logic is in `shell-mpc/plugin_paths.h`.

## Install on the MPC

Copy the whole folder `Safian - VST - SynthyBoy` into a folder named exactly `VST2 Plugins` at the root of a USB drive, SD card, or the MPC's internal drive. The MPC must be running MPC OS 3.10.1 or later. In **Preferences → Enhancements (Beta)** turn on both **Enable Enhancements** and **External Plugin Support**; the plugin stays hidden until both switches are on. After inserting the drive, open the plugin browser (instrument track → plugin program → browse, or an insert slot). The plugin is listed under **External Plugins**.

Replacing a plugin: copy the new folder over the old one, then remove and re-add the plugin on the track (or restart the MPC if the skins changed). Uninstalling: delete the folder from `VST2 Plugins`. Projects that used it will load without the plugin.

## Known host behaviour

### Observed on the device

Seen on an MPC Key 61 with firmware 3.10.1:

- The host runs plugins at 44.1 kHz with 128 frame blocks.
- There is no plugin GUI. The screen pages come from Plugin Skins (`TUI.json`), and the hardware knobs are mapped from `Q-Links.json`.
- A newly copied plugin appears only after the MPC application is restarted.
- The plugin runs inside the MPC's process. For that reason the shell wraps the instance creation and every dispatch call in `catch (...)` (no instance, or a result of 0), so no exception leaves the plugin.
- A module built with Zig crashed when the host exited (see Build): the module is built with GCC.
- The packaged plugin loads in the stock MPC app; stepping through the presets works; the generated skin with its 30 pages works (the skin of that check had 30 pages, one function key each; the later skins with the Env, Osc and LFO tab layouts and the sub-tabs were tried one by one, see "Function keys and sub-tabs"); the owner checked the sound by ear (it plays without crackling).

Measured on 2026-11-13 with the bench on the device (MPC Key 61, 44.1 kHz, 128 frame blocks, so one block lasts 2.902 ms; tier low, own engine):

- Basic patch, 8 notes held: block time average 0.535 ms, 99th percentile 0.789 ms, worst 1.405 ms.
- Idle (no notes): 0.022 ms per block. Each additional note costs about 0.070 ms per block.
- Note-on of 8 notes: average 0.97 ms, worst 1.34 ms.
- Preparing the engine (prepare) takes 542 ms.

- The bench option `--ftz` makes no difference to these times.

What follows from these numbers:

- The synthetic heavy patch with 8 notes does not fit into the 2.902 ms block even without unison (cap 1). The earlier measurement of it, at engine commit `878326f`, was cap 3: average 4.42 ms, 99th percentile 6.35 ms, worst 6.83 ms. In the final state (engine commit `91f2d75`, tier low, unison cap 3, 3 s, retrigger after 1000 s, so no retrigger inside the run) the heavy patch gives, as average / 99th percentile / worst block: 8 notes 3.354 / 3.691 / 3.959 ms, 6 notes 2.637 / 2.868 / 3.781 ms, 4 notes 2.059 / 2.595 / 3.205 ms. The basic patch with 8 notes (10 s) gives 0.474 / 0.703 / 0.965 ms. So the heavy patch does not fit safely with 8 or 6 notes (with 8 notes even the average is above the block; with 6 notes the average and the 99th percentile are just below it and the worst block is above it); with 4 notes the average and the 99th percentile are below the block and the worst block is above it. The factory presets are lighter than the synthetic heavy patch.
- The 112 factory presets do fit with 8 notes (see the table above), so no cap on the number of notes is needed. No decision about such a cap is pending.
- The default of the unison cap is 3; that there is a cap is the owner's decision. A cap of 3 affects 14 of the 112 factory presets (`scripts/preset-unison-report.py` lists every preset): Fat Reese, Cosmic Drift Lead, Hyper Saw Lead, Diffusor Cloud Pad, Ethereal Glass, Frozen Aurora, Harmonic Cloud, Infinite Horizon, Lush Analog Pad, Space Odyssey Pad, Tri-Band Split Texture, Velvet Strings, Vintage Brass Pad, Pizzicato Strings. ### Per the SDK documentation / not yet verified on the device

These statements come from the SDK's documents (host-contract.md, install-and-test.md). A project was saved and loaded once (see above), but in which order the host restores the program and the chunk was not observed, so the host side of the program handling below is unconfirmed. Still not verified on the device: the CPU load during playback in the MPC app, and the sound of the final build (shell commit `17d6e11`): it loads in the stock MPC app, but nobody has listened to it.

- The sample rate is fixed, and the user can choose other block sizes (32, 64, 96, 192, 256, 512) in Preferences; the announced block size is a maximum. The shell handles any smaller count.
- The host has no crash protection for plugins: a crash in the plugin takes the MPC application down.
- The host selects program 0 after loading and reads every program name by index.
- The host saves the program number and the plugin's chunk in the project and restores both on load. In which order it does so, and whether it selects the saved program again after restoring the chunk, is not known.

What the shell does with programs and the chunk is its own behaviour and is covered by the acceptance tests, whatever the host's order turns out to be. `effGetChunk` returns a JSON text starting with `{"mpcProgram":N,"mpcProgramName":"<escaped name>",` followed by the engine state. On `effSetChunk` the shell reads the program number and name and calls `resolveProgram` to map them to the current preset list. The name decides: the stored index is used only if the program at that index has that name (or to choose between programs of the same name), otherwise the first program of that name is taken, so a project still finds its program when a later package has a different preset list. A chunk from an older build that has only the number still loads. If the name is not in the list, `resolveProgram` returns -1 and the shell enters a "no program" state: the sound is the one stored in the chunk, the host is given index 0, the saved name is shown as the program name and written into the next chunk again. In case the host selects the saved program number again right after restoring the chunk, that one selection is ignored (the chunk wins); any other program selection or a parameter edit ends this protection, and it is never armed in the "no program" state.

## Envelope tabs (Env 1 - Env 4)

The four envelopes have a tab each (`Env 1` .. `Env 4`, the sub-tabs of the function key `Env`). `scripts/mpc-skin-extras/10_env.py`
(run after the SDK `gen_ui.py` by `scripts/apply-mpc-skin-extras.py`) puts a full-width editable curve (SDK `Envelope`,
`envelopeType` `DAHDSR`) on the top two rows of each tab. Dragging a stage handle sets `envN.delay`, `attack`, `hold`, `decay`, `sustain`
or `release`.

- The curve draws straight segments between the handles. The curvature parameters (`attack_curve`, `decay_curve`) stay knobs.
- The stage widths are proportional to the normalized parameter value (a linear scale over the whole parameter range; the SDK `Envelope`
  has no skew or per-stage width key, checked in the SDK reference and in all five factory skins), so short times are narrow.
- The eight knobs sit in the lower two rows and are Q-Link 1-8 (the generator's own Q-Link map of the tab is rewritten to match; the Q frames mark the lower two rows).
  `Env 1 Release` has a knob on this tab as well as on `Macros` (the generator places a parameter once; the module adds the second knob).
- `scaleColour` is `0`: with a visible scale colour the host draws a column of scale lines at the right edge, far from the curve.
- Double tap (or Enter) on the curve opens a full-screen editor (`EnvelopeOverlay`, definitions `envOverlayN`). Observed on the Key 61
  (MPC 3.10.1.12): an `EnvelopeOverlay` definition in `localComponentDefinitions` is only loaded when it carries the complete key set of the
  factory Sub Factory `DAHDSR` envelope, i.e. the three shape handles, `forceHideShapeHandles`, `forceCurveShape`,
  `decayAndReleaseCurvesLinked` and `curveType`. With the minimal SDK-table key sets (`ADSR`, `AD`, `AHDS`, `Pumper`) the host drops the
  whole skin (empty plugin page, no log message), even when nothing refers to the definition. The `Envelope` element on the tab carries the same key set.
- The shape handles `AttackShape`, `DecayShape` and `ReleaseShape` are bound to `envN.attack_curve`, `decay_curve` and `release_curve`
  (all three have the range -20..20, 0 in the middle, and the SDK shape value 0.5 is the straight line, so the middle of the range matches).
  Whether the drawn curvature follows the engine's curve exactly is not verified on the device.

## Oscillator wave pictures (skin)

The tabs `Osc 1`, `Osc 2` and `Osc 3` of the generated skin show the selected wavetable as a large picture (512 x 240 pixels, centred in the upper two rows of the 4 x 4 grid) above the 8 knobs of the oscillator (`oscN_main`, rows 3 and 4, Q-Link 1 to 8: the rows on the screen are the rows of the hardware). The unison and the shaping knobs are on the tabs `Osc1 Shp`, `Osc2 Shp`, `Osc3 Shp`. The picture is made by `scripts/mpc-skin-extras/20_osc.py` (after the SDK `gen_ui.py`, see `scripts/mpc-skin-extras/README.md`).

- **Source**: the frames of the built-in tables of the own engine (`core/engine-own/osc/wavetable_bank.cpp`, the engine of this build), every harmonic kept, written by the host tool `tools/mpc-wave-dump/wt_dump.cpp` and drawn by `scripts/gen-mpc-wave-strips.py` into `scripts/mpc-skin-extras/osc-wave-strips/osc_wt_00.png` .. `osc_wt_14.png` (committed; the build does not need numpy, Pillow or a compiler). Nothing is drawn by hand; a test renders them again and compares with the committed files. Run `python3 scripts/gen-mpc-wave-strips.py` after a change of a table.
- **One strip per table, shared**: one `Image` film strip per `oscN.wavetable` choice, bound to `oscN.frame`. It is valid, so visible, only while `oscN.wavetable` has that choice (`IndexedEnabling/<choice>/15/Parameter <N>`, bounds version 2). The three oscillators use the same 15 files.
- **Frames**: the tables of one cycle (Sine, Saw, Square, Triangle, the quarter pulse, Saw Down) have one frame in the engine and a one frame picture. The eight morphing tables (Saw to Square, Sine to Saw, Harmonic Series, Odd Harmonics, Formant Sweep, FM Sweep, PWM Sweep, Bell Partials; 64 engine frames) have 16 frames. "Preset table" has one neutral picture marked PRESET: the table of a preset is its own and the skin does not know it.
- **Frame position**: the device shows frame `floor (v * (n - 1))` of an `n` frame strip for the parameter value `v` (0 to 1), so the last frame only comes at the very top of the range. Frame `i` before the last therefore shows the table at the middle of its interval, `(i + 0.5) / (n - 1)`, and the last frame shows the table at its end; between two engine frames the picture is the linear mix of the two cycles.
- **Memory**: the host probably keeps the pictures decoded, width x height x frames x 4 bytes. 512 x 240 x 4 = 491 520 bytes per frame; 8 strips x 16 frames + 7 pictures of one frame = 135 frames; 135 x 491 520 = 66 355 200 bytes = 63.3 MiB, under the limit of 64 MiB. More frames or a bigger picture do not fit: for example 64 frames at this size would be 8 x 64 x 491 520 = 251 658 240 bytes (240 MiB). On disk the 15 files are about 2.1 MB.
- **What the picture does not show**: the effect of morph and warp. The skin cannot draw a live curve (the `Info/Named/...` data channels of the factory plugins are inside the host; nothing in the VST2 interface lets a plugin feed them), so the picture is the table itself at the frame position.

## Sound differences at tier low

The MPC build runs the engine at `Tier::low` (`core/include/synthyboy/quality.h`). Everything below applies only at that tier; the other tiers and the offline render (which runs on an engine at the high tier) are not changed by it, and the stored parameter values and the saved state are never changed, so a preset keeps its shape and a project saved on the MPC sounds in full on a desktop. Error bounds are absolute for a signal whose full scale is 1, unless they are called relative.

- **Unison cap**: at most 3 unison voices per oscillator (the tier's own cap is 4). A patch that asks for 7 voices sounds like the same patch with 3: the same detune width, stereo spread, blend and level law. `setLowTierUnisonCap` changes the number (0 = no cap).
- **Warps**: a warped oscillator runs 2x oversampled with a 32-tap Kaiser decimator instead of 4x with 128 taps, so extreme warps alias a little more and the warped oscillator is about 8 instead of 16 samples late. The table band limit of a warped oscillator is 1.0 times the host rate instead of 3.2 times. The decimator sums its taps in four partial sums (relative difference about 1e-7).
- **Spectral morph**: the morph cycle is rebuilt every 512 samples instead of every 256, so a modulated morph lags by up to about 12 milliseconds instead of 6. The cycle comes from a transform of half the size (difference to the full transform 4e-7). By default the unison voices keep the morph spread (two cycles); `setLowTierMorphSpread(false)` shares one cycle between them. A new note builds its morph cycle at once (this also fixed a bug that left the first period of a morphing note stale).
- **tanh** is a [7/6] Pade rational function with an absolute error below 1e-4 (clamped to plus or minus 1 beyond 4.972) in the classic filter models (the limiter of the Digital model, Ladder, Diode, Dirty), the phaser feedback, the distortion shapes and the warps.
- **sin and cos** come from a 1024-entry table with linear interpolation (error below 5e-6): the chorus LFO, the sine shaper of the distortion, the bend, sine fold and sine shaper warps.
- **exp, exp2, pow, 10 to the power x and log2** are polynomial forms (exp2 relative error about 3e-9, exp, 10^x and pow about 1e-6, log2 absolute 6e-8) in the phaser, the distortion drive and shapes, the compressor's power terms and the modulated parameter values.
- **Moving filters**: for the Ladder and the state variable models (Analog, Dirty, Digital) with a moving cutoff the setup (tan, powers, square roots) is computed at both ends of the 32-sample control period and interpolated linearly over four pieces of 8 samples (relative difference about 1e-4); both channels run in one loop with one setup. The Diode divides by constants of the block through reciprocals (a few units in the last place), and the Ladder divides by `1 + k G^4` through a reciprocal (1 unit in the last place).
- **Serum filters**: the smoothed cutoff and resonance that the filter runs on are held for 4 samples (the coefficient lags the smoothed cutoff by at most 3 samples of a 30 Hz one-pole filter).
- **Economy modulators**: LFOs, random LFOs and envelopes 2 to 6 that no modulation slot or custom shape reads are stepped every fourth control period instead of every period; their displayed values are up to 1.4 milliseconds old, and a route added during a note finds them at the phase they have.
- **Chorus and phaser**: the chorus delay times are held for 4 samples (a change below 0.004 samples), and the phaser stage and band coefficients are updated every 8 samples (a few thousandths of an octave).
- **Noise**: the six uniform numbers of the Gaussian noise come from three draws of the generator (16 bits from each half); the variance and the colour are the same, the random sequence is a different one.
- **Effect racks on silence**: a rack whose input has been exactly zero and whose output has stayed below minus 120 decibels full scale for longer than the longest gap between echoes (20 seconds if a delay or a pool slot is in the rack, 1 second otherwise) is not processed; its LFOs keep their pace through `idleAdvance` calls, and the rack wakes with the first non-zero input.
- **Stolen voices**: when a note is stolen (Kill mode) the voice stops at once and its last output sample on each bus is faded to zero in 3 milliseconds by the engine (`setLowTierKillFade`; the medium and high tiers let the voice itself fade in 50 milliseconds). The ramp is a held value, like a short thump, not the voice's own sound.
- **Events**: note and controller events take effect at the start of the 32-sample control period that contains their frame, up to 0.73 milliseconds early, instead of sample accurately; a block is no longer cut into pieces by events.
- **Bypassed effects and polyphony**: `Tier::low` bypasses reverb, flanger, Hyper/Dimension, Bode, and Convolve (the bit mask in `quality.h`). A preset that uses them plays without them. The remaining effects (chorus, compressor, delay, distortion, EQ, the effect filter, phaser) are still active. The tier caps polyphony at 8 voices.

Changes that do not alter the sound at any tier (they compute the same samples with less work) are not listed here: caches of filter and morph results, coefficients computed once per block, no work for sources that are switched off, NEON loops that equal the scalar code bit for bit, and the exact floor.

## Benchmark switches

The benchmark `synthyboy_bench` (`bench/bench_engine.cpp`) and `synthyboy_noteon_bench` run on the device as they are (built by `scripts/build-mpc.sh --bench`, or by `cmake` for the armv7 / aarch64 toolchain with `-DSYNTHYBOY_BUILD_TESTS=ON`). The switches used for the measurements above:

## LFO pictures

The tabs `LFO 1` to `LFO 4` (sub-tabs of the function key `LFO`) have the same layout as the Env and Osc tabs: a large picture of the selected shape in the upper two rows, with a cursor that follows the cycle of the voice that was played last, and the eight main controls of the LFO in the lower two rows, which are Q-Link 1 to 8 (the rows on the screen are the rows of the hardware): Shape, Sync, Rate, Division / Trigger, Phase, Fade In, Delay. The Q-Link frames cover the lower two rows (`x 301 288 323`, see "Q-Link frames and alignment"). `scripts/mpc-skin-extras/30_lfo.py` builds the tab.

- **Two layers.** The host keeps film strips and pictures decoded (width x height x 4 bytes per frame), so one strip of 33 frames per shape at this size would not fit. (a) The shape: 13 single frame PNGs, 600 x 240 pixels (the 12 shapes of the engine's `lfoShape()` and CUSTOM), one `Image` each, valid only while `lfoN.shape` has that choice (`IndexedEnabling/<choice>/13/Parameter <shape>`, bounds version 2), centred in the tab at `340 30 600 240` (y 30 to 270, above the frames). (b) Over it ONE transparent film strip, `lfo_cursor.png`, 33 frames of 600 x 240 (7920 pixels tall): frame 0 is empty (no voice sounds), frames 1 to 32 have only a vertical line, 3 pixels wide, in one cell of the cycle; the cell centres are at x = 24 + (k - 0.5) / 32 x 552, the curve of layer (a) uses the same x. The same file serves the four LFOs and every shape; it is bound to the display parameter "LFO N Cursor" and is shown for every shape (also for CUSTOM).
- **Source and size.** The curves are the engine's: `scripts/gen-mpc-lfo-pictures.py` compiles `scripts/lfo-shape-dump.cpp` against `core/engine-own/env_lfo/lfo.h` and plots its samples (red line, faint fill, grid, the shape name at the top left, like the oscillator pictures); the result is committed in `scripts/mpc-skin-extras/lfo-pictures/` (`lfo_shape_00.png` .. `lfo_shape_12.png`, `lfo_cursor.png`; run the script after a change of the LFO code, a test renders them again and compares; needs numpy, Pillow and a C++ compiler, the build only copies the files). Decoded: (13 + 33) x 600 x 240 x 4 = 26 496 000 bytes, under the budget of 32 MB (a test); the files are 0.2 MB on disk. All PNG files of the skin together are 105 709 408 bytes decoded (the wavetable pictures 66 355 200, these pictures 26 496 000, the kit 12 825 568, the spectrum columns 32 640; before the large LFO pictures the skin had 96 267 744 with 12 551 552 for the 208 x 38 strips); a test keeps that number. The 208 x 38 strips of the earlier version (12.5 MB decoded) and the tabs `LFO 1-2` and `LFO 3-4` are gone.
- **Transparency.** The cursor strip is an RGBA PNG whose background is fully transparent; the host has to draw the picture below it through it. Evidence: the knob, fader, toggle and button images of the SDK kit are RGBA PNGs with fully transparent corners (`knob_uni.png`: pixel 0,0 is 0,0,0,0) and every skin built from the kit uses them over the dark page background, including the skins loaded on the Key 61 (no screenshot of that was examined for this document), so the host is expected to blend the alpha channel of an `Image` / film strip. That the host blends it over another `Image` (not over the page background) was not measured separately; it is the same drawing call, and the cursor frames carry the light line colour also on their partly transparent edge pixels, so that a host that treated them as opaque would show a bright line and no dark box.
- **Sync.** The rate in Hz matters only when `lfoN.sync` is "Free (Hz)", the division only for the three tempo modes, "Key follow" uses neither (`lfoRateHz` in `core/engine-own/env_lfo/lfo.h`: 0 free, 1 tempo, 2 dotted, 3 triplet, 4 key follow). A Q-Link is one parameter, so Rate and Division cannot share one place in the Q-Link map: they keep their two places and the one that does not apply is hidden. Rate is valid for sync 0 (`IndexedEnabling/0/5/Parameter <sync>`); the Division exists three times at its place, each copy valid for one of sync 1, 2 and 3 (the same `IndexedEnabling`, which is the proven mechanism; the copies are named `LFO N Division`, `LFO N Division 2`, `LFO N Division 3`). With "Key follow" both places are empty. The knob name of Rate has the same visibility (85_names.py); a hidden control cannot take focus but its Q-Link still moves its parameter.
- **Controls and Q-Links.** The eight controls are those of the Kick page `lfoN`; the selectors Shape, Sync, Division and Trigger have the host header, Rate, Phase, Fade In and Delay are knobs. `Q-Links.json` of the tab: row 3 (Q-Link 5 to 8) Shape, Sync, Rate, Division; row 4 (Q-Link 1 to 4) Trigger, Phase, Fade In, Delay.

The frame follows a display-only plugin parameter, "LFO N Cursor", at the end of the parameter list (index: number of engine parameters plus N minus 1), holding the step divided by 32. The values are not saved in the state or a preset, the parameters are not automatable and no index before them moves. Because the host redraws only on `audioMasterAutomate`, a thread of the shell (`shell-mpc/synthyboy_mpc.cpp`, `shell-mpc/lfo_live.h`) reads the engine's live values (`LiveValues::lfoPhase`, the voice played last) and calls `audioMasterAutomate` only for a cursor that changed cell.

Thread model of the display (the reason is the host: `audioMasterAutomate` runs synchronously on the host's interface thread, and a continuously moving display was reported by the community wrapper "Open MPC" (`wrapper/vst2_wrap.c`, a comment there; measured by its authors on an MPC Live III) to hold up the host's audio threads for about 20 milliseconds every few seconds; that wrapper therefore reports from a separate thread of normal priority, every 100 milliseconds, changed values only):

- One display thread per plugin instance, created in `VSTPluginMain` (the host's loader thread, not the audio thread; whatever that thread is, the display thread sets its own scheduling first, see below). Tick rate `SYNTHYBOY_MPC_LFO_LIVE_HZ`, default 10: a tick every 100 milliseconds. A tick reads the cursor positions at that moment (the cursor is always where the cycle is now, not a queue of old positions), and calls `audioMasterAutomate` for each of the four parameters whose cell changed, in index order, at most once per parameter and tick. With a fast LFO the 32 cells are therefore stepped over (the cursor jumps), which is accepted. A tick that comes late (the host call blocked) is not made up for: one tick, then the grid goes on from that moment. With no voice sounding the thread looks every 100 milliseconds and does not call the host.
- The thread is a normal thread: `shell-mpc/thread_policy.h` sets, from inside the thread, policy `SCHED_OTHER` with priority 0, nice 0 and the affinity of all CPUs. Nothing is inherited from the thread that created the plugin: a real-time policy or a single-core affinity of the creator would otherwise carry over to a `std::thread`. Nice 0 (not lower) because the thread holds host locks while it is inside the host call, and a starved holder makes the host's own threads wait. Lowering a nice value needs the privilege `CAP_SYS_NICE`; a host process without it keeps a nice value inherited from a creator with nice above 0 (policy and affinity are always reset). The thread is named `sb-lfo-display` (`top -H`, `/proc/<pid>/task/<tid>/comm`). The host test (`shell-mpc/tests/lfo_live_host.cpp`, Linux) creates the plugin from a thread that is pinned to one CPU and, where the process may, nice 5 and `SCHED_FIFO`, and checks policy, nice and affinity of the display thread; it ran on aarch64 Linux in a container, with and without `CAP_SYS_NICE`.
- The audio thread (`pluginProcessReplacing`) does nothing for the display: no call to the host for it (its one host call is the transport query `audioMasterGetTime`, as before the display existed), no allocation, no lock. The only connection is that the engine writes its readout (`OwnEngine::writeReadout`, relaxed atomic stores) at the end of a block, and the display thread reads those atomics (`copyReadout`) and the parameter mirror. The cursor values the host reads (`getParameter`) are atomics too.

Callback statistics (diagnostics, off by default). To find out on the device whether the display holds up the audio callback, the shell can measure its own callback: build with `-DSYNTHYBOY_MPC_CALLBACK_STATS=ON` (compile switch `SYNTHYBOY_MPC_CALLBACK_STATS`, default 0; with 0 the source preprocesses to exactly the text without the statistics code). In `processReplacing` it measures with the monotonic clock the time between two calls (the gap) against the nominal block time of the previous block (frames divided by the sample rate), and the time spent inside the call. On the audio thread this is arithmetic and relaxed atomic stores into storage that exists from the start: no allocation, no lock, no file access (`shell-mpc/callback_stats.h`). A low priority thread (`sb-cb-stats`, nice 10) writes a text file every 5 seconds and when the plugin is closed, through a temporary file and rename. Environment variables of the host process: `SYNTHYBOY_MPC_CALLBACK_STATS_FILE` (default `/tmp/synthyboy-callback-stats.txt`; a second plugin instance writes `<file>.2`, and so on) and `SYNTHYBOY_MPC_CALLBACK_STATS_INTERVAL_MS` (default 5000). The sections after the callback lines (added in format 2; the sample above is shortened and its numbers are illustrative) answer two questions on the machine itself. `midi:` counts every message that arrives in `effProcessEvents` by status type (note off, note on, polyphonic aftertouch, control change, program change, channel pressure, pitch bend; everything from 0xF0 on, and a first byte below 0x80, as `system_or_other`) and per channel (channels with no message are not listed), counts each control change number (non zero rows only), keeps the smallest and largest pitch bend (14 bit), channel pressure, polyphonic aftertouch value and CC 74 value seen, and lists the last 64 messages (time since the plugin was created, position in the block, status and data bytes). `vst_events` also counts the events that are not MIDI messages: sysex events (type 6) and events of any other type. `host_can_do:` lists every different `effCanDo` text the host asked (at most 32 texts of 63 bytes, how often, and the answer the plugin gave last); `dispatcher_opcodes:` counts every call of the dispatcher by opcode with the name from the ABI header (opcodes the header does not know are named `unknown_to_the_ABI_header`) and shows the index, value, opt and whether `ptr` was set for the first 8 calls of `effVendorSpecific` and of the first 8 calls with an unknown opcode; `audio_master_calls:` counts the plugin's own calls to the host by opcode. Known limits of the cursor, from the engine's readout: swing and direction are not drawn; in free-run mode and for mono envelope LFOs the engine does not advance the voice's own position, so the cursor stays at the start; an envelope-type LFO that has finished jumps back to the start; with several voices only the voice played last is shown.

The skin refers to the display parameters, so the MPC plugin must be built with them. Build options of the MPC shell (CMake): `SYNTHYBOY_MPC_LFO_LIVE` (default ON; OFF builds the plugin without the parameters, only for comparisons, because then the host hides the pictures), `SYNTHYBOY_MPC_LFO_LIVE_HZ` (default 10, ticks a second), `SYNTHYBOY_MPC_LFO_LIVE_NOTIFY` (default ON; OFF updates the values without telling the host, a baseline), `SYNTHYBOY_MPC_LFO_LIVE_SELFTEST` (default OFF; the cursors sweep without a note, for measuring on the host), `SYNTHYBOY_MPC_CALLBACK_STATS` (default OFF; the statistics above). The compile switch of the same names in the source defaults to 0, which makes the shell identical to one without the display. The acceptance script `shell-mpc/accept.sh` builds the variants (also HZ 25 and the statistics) and runs the ON build, with the statistics, under ThreadSanitizer.

A `Plotter` bound to a parameter does not draw on this host (see the device observations), so the display is a film strip and not a plotted line.

## Spectrum

The bottom row of the `Macros` tab (the fourth row of the grid is empty there) shows a live spectrum of the plugin's own output: 32 vertical columns, from about 30 Hz to 18 kHz on a logarithmic scale, 30 pixels wide with 8 pixels between them (32 x 30 + 31 x 8 = 1208 pixels, centred, x 36 to 1244), y 480 to 616. `scripts/mpc-skin-extras/40_spectrum.py` builds them; the Q-Link frames of the tab end at y 474 (rows 1 to 3), so the columns, which cross the four frames, stand below them.

- **Widget.** One native `Meter` per column, `direction "Up"`, with the keys and the key order of the Filterbank's `envfollower_meter1` element (`version 3`, `invert false`, `inactiveImage`, `rmsImage ""`, `rmsHandle "Invalid"`, `peakImage`, `peakHandle`, `peakHoldHandle`, `peakHoldSize 0`, `peakHoldColour`) and the remap `Data -> Parameter N`; `peakHandle` is `Parameter N`, `peakHoldHandle` is `Hold/Parameter N`. A film strip per column was the first plan and is not used: a Meter bound to a plugin parameter works on the Key 61 (see the device observations), it needs two small pictures shared by all 32 columns and not a strip per column, and the level is continuous. The `Plotter` does not draw a parameter, and the `Info/Named` channel that feeds the stock plugins' displays has no known way for an external plugin. `"Right"` was the direction tried first; `"Up"`, the one the stock output meters use, was tried on the Key 61 afterwards and works (see the device observations).
- **Pictures.** `scripts/gen-mpc-spectrum-images.py` (standard library only, deterministic) writes `scripts/mpc-skin-extras/spectrum-images/spectrum_off.png` (dark, 42 41 44) and `spectrum_on.png` (the accent colour, a vertical gradient from 244 63 110 at the top to 211 17 69 at the bottom), both 30 x 136 pixels; a test regenerates them and compares the bytes. Decoded they are 2 x 30 x 136 x 4 = 32 640 bytes, so they add nothing to the 105 709 408 bytes of the skin ("LFO pictures").
- **Parameters.** 32 display-only parameters "Spectrum 1" to "Spectrum 32" at the end of the list, after the four LFO cursors: indices 2641 to 2672 (2637 engine parameters, 2637 to 2640 the cursors). Value 0 to 1 in steps of 1/64 (display text "n/64"). They are not in the mirror, the state chunk or a preset, `effCanBeAutomated` is 0, writes are ignored, no index before them moves (a test checks the names, the indices and that the chunk is the same with and without them).
- **Thread model.** The audio thread (`pluginProcessReplacing`) copies the mono sum (left + right) / 2 of the engine's output, after the engine has rendered the block, into a ring of 8192 samples (`SpectrumRing` in `shell-mpc/spectrum.h`: relaxed atomic floats, the write position released after the samples): no allocation, no lock, no call to the host. The display thread of the LFO cursors (`sb-lfo-display`, normal priority, 10 ticks a second by default) does the rest on every tick: the newest 2048 samples (about 46 milliseconds at 44.1 kHz), Hann window, FFT (`shell-mpc/spectrum_fft.h`, own radix-2, no dependency), 32 bands with equal ratio from 30 Hz to 18 kHz (`shell-mpc/spectrum_bands.h`; a band takes the largest bin inside it, a band narrower than a bin interpolates between the two neighbouring bins, so the lowest columns share bins: at 44.1 kHz a bin is 21.5 Hz wide), to dB (a full scale sine on a bin gives 0 dB), to a level (linear in dB from floor `kSpectrumFloorDb` = -60 dB -> 0 to ceiling `kSpectrumCeilingDb` = -12 dB -> 1, clamped to 0..1: levels above -12 dB show a full column because on the device a single loud note peaked at about half height with the earlier 0 dB ceiling, as a single band never reaches 0 dB), smoothing (the distance to a higher target is covered by 0.7 per tick, to a lower one by 0.15, about 3 seconds from the top to nothing at 10 ticks a second), quantised to 1/64 so that a small flutter makes no report. Every column whose quantised value changed is reported with `audioMasterAutomate` in index order: at most 32 calls a tick besides the at most 4 of the cursors, none while all columns stand on the floor. A ring that did not move since the last tick (the host stopped calling) counts as silence.
- **Build options (CMake).** `SYNTHYBOY_MPC_SPECTRUM` (default ON in `shell-mpc`; the source default is 0, so a build that does not define it has no spectrum code, no parameter and no string of it; it needs `SYNTHYBOY_MPC_LFO_LIVE`, the thread is shared) and `SYNTHYBOY_MPC_SPECTRUM_SELFTEST` (default OFF; a wave runs over the 32 columns without a sound, for measuring the host side; at `SYNTHYBOY_MPC_LFO_LIVE_HZ=25` it is the worst case, 32 reports every 40 milliseconds). The skin of `40_spectrum.py` refers to the parameters, so the MPC package must be built with the spectrum ON.
- **Tests.** `shell-mpc/tests/spectrum_bands_host.cpp` (the band mapping on a 1 kHz sine, other sines, silence, white noise, the quantiser), `shell-mpc/tests/spectrum_host.cpp` (ring and analyser: silence, a sine, the smoothing, a stale ring, two threads), `shell-mpc/tests/spectrum_live_host.cpp` (the plugin: parameter count and names, silence gives no report, a held note moves the columns to where an offline analysis of the same output puts them, at most 32 calls a tick, the reports stop after the note, the self-test wave), all three also under ThreadSanitizer through `shell-mpc/accept.sh`; `scripts/tests/test_mpc_skin_spectrum.py` (the elements, the handles, the geometry) and `scripts/tests/test_mpc_spectrum_images.py`.
- **The curve over the meters (overlay build).** In a build with `SYNTHYBOY_MPC_OVERLAY` and the overlay skin, the Macros tab shows the same signal a second way: one smooth, filled, anti-aliased spectrum CURVE (Serum / EQ analyser style) exactly over the row of the 32 meters, the view `spectrum` of "Overlay (experimental)". The meters stay in the skin underneath and are what is seen when the overlay is off, disabled, or has no data (an instance without the spectrum ring); the production skin and the production plugin do not change. Where the picture comes from: nothing new on the audio thread, the curve reads the same ring `SpectrumRing` as the meters; the analysis is `shell-mpc/overlay/spectrum_curve.h` on the overlay thread, and it runs only while that tab is on screen, once per picture (about 30 a second, and not at all in silence).
  - FFT of 4096 samples with a Hann window, hopping by one picture (about 33 milliseconds, so a new analysis overlaps the last by about 65 percent). At 44.1 kHz the window is 93 milliseconds and a bin is 10.8 Hz: the partials of a note from about 40 Hz up are separate peaks (the 2048 samples of the meters would show the lowest octave as one lump), and a longer window would smear the attack of a note. The mean of the window is taken out first (a DC offset of the output is not sound and would show as a hump at the low end).
  - Level: `S[k]` is the power in the three bins of the Hann main lobe divided by 1.5 (the noise bandwidth of the window), so a sine gives its own amplitude whatever its distance from a bin centre (a plain bin read-out loses up to 1.4 dB between two bins), and the dB scale is the one of the meters (`kSpectrumFloorDb` at the bottom to `kSpectrumCeilingDb` at the top, the same constants, a full scale sine is over the top).
  - 256 points, log axis from 20 Hz to 20 kHz. A point narrower than a bin (the low end) is interpolated between the two bins; a point narrower than the main lobe (up to about 1.5 kHz) takes the peak of `S` over its stretch, so a tone keeps its level wherever it lies between two points; a point wider than 12 bins (above about 3 kHz) takes the mean of `S` over its stretch (the integral of the interpolation divided by the width): noise is flat, the high end calm, and a narrow tone is spread over the point and reads lower by about 10 log10 (bins covered / 3). In between the two are crossfaded.
  - Light smoothing across frequency: a point is raised towards the mean of itself and its two neighbours, never lowered (valleys between partials fill a little, every peak keeps its height). In time, per point: attack with a time constant of 20 milliseconds, release with 350 milliseconds, by the real time between two analyses; a point under 1/256 of the scale with a target at the floor goes to exactly 0.
  - Silence: a window whose largest sample is under -80 dB below full scale (far under the floor of the scale), or a ring that did not move (the host stopped calling), is not analysed (no FFT); the curve falls to the floor and, when it has settled there, the view reports "unchanged": no picture is drawn, the helper sleeps, the thread polls. The 32 display parameters and their reports are not touched.
  - Drawing: an opaque dark background over the whole row (the meters do not show through), faint grid lines at 100 Hz, 1 kHz and 10 kHz, a filled area under the curve with a vertical gradient (accent colour, strong under the line, almost transparent at the bottom) and a line 2.5 pixels thick in the accent colour, 30 pictures a second while the curve moves. The same picture from the GPU (a scene with the gradient fill, protocol version 2) and from the CPU (`draw.h`, `fillToBaselineGradient`); the geometry of the row is `meterRow` in `shell-mpc/overlay/overlay_layout.json`, the one place that both `40_spectrum.py` and the overlay read.
  - Tests: `shell-mpc/overlay/tests/spectrum_curve_host.cpp` (sines at several frequencies and levels, the worst offset of a tone between two points, two sines, a DC offset, white noise, silence, a ring that stands still, the attack and release times, other sample rates, the audio thread pushing while the overlay thread analyses, also under ThreadSanitizer through `shell-mpc/accept.sh`), `shell-mpc/overlay/tests/spectrum_view_host.cpp` (the view and the controller: no data without a ring, the scene is the CPU picture, no picture at rest). The measured numbers are in "Known host behaviour".
- **Limits.** The spectrum is the sum of both output channels of the plugin, not the stereo image; the plugin's own effects are in it. A pure tone shows in the column of its band and a little in the neighbours (the Hann window). The audio callback gaps with the 32 columns are in "Known host behaviour" (Key 61 with the self-test wave and with a real chord, MPC XL with the self-test wave); the CPU cost of the analysis on its own (about one FFT of 2048 points per tick) has not been measured, nor has how the peak hold looks or the MPC XL with real sound in the test project.

## Control names

The tab says which module a control belongs to, so the name over a knob, toggle, fader or radio group is short: "Detune Curve" instead of "Osc 1 Unison Detune Curve". The host draws the name of such a control from the parameter name (a `Label` of type `Name` in the shared component definition); `scripts/mpc-skin-extras/85_names.py` removes that child from the definitions and puts a fixed text (`Label`, type `Text`) over every control, at the place where the host drew the name. The same module gives the label the `additionalInvalidatingHandles` of its control, so a control that is valid for one choice of another parameter only shows its name only then.

- **Where the names come from** (`scripts/gen-mpc-ui.py`, which writes them with the page structure to `skin-meta.json` next to `ui.json`; the build passes that file to `scripts/apply-mpc-skin-extras.py --meta`): the `shortLabel` of the Kick page (`docs/kick-pages.json`), unless `scripts/mpc-short-names.json` has an entry for the parameter key. The table holds the names where the `shortLabel` is cut off at 10 characters ("Unison Ste", "Key Tracki", "Voice Cont") or is ambiguous, and the few that were too wide. If two controls of one tab still get the same name, the generator puts in front of the name the words in front of the longest common word suffix of the full parameter names: "Osc 1 Filt Blend", "Osc 2 Filt Blend", "Filter 1 Dest", "Mod 01 Source". The rule is deterministic; a clash it cannot resolve (no common suffix) stops the generator and asks for table entries. Tests: names are unique inside a tab, none is cut off in the middle of a word, no name is wider than the area.
- **Style**: Titillium Web SemiBold 22 pixels, upper case (`case` `Upper Case`), colour `ff6a6a6c`, the weight of the headers the host draws over the selectors ("OSC 1 MORPH TYPE"); the value below keeps white and 24 pixels. The colour is the SDK's own "muted" grey (`tools/gen_ui.py` `DEFAULT_STYLE`, used by the generated name labels before); the font and size of the header drawn by the host are not in any file (the Slider draws them inside the host), so bold and about 22 pixels follow the description of the header seen on the device. The label is 272 x 26 pixels at the top of the slot (the knob and toggle slots at y 0, the faders at y 4, the radio groups at y 6).
- **Width**: the width of a name is estimated from the advance widths of Titillium Web Bold (`ADVANCE` in `scripts/gen-mpc-ui.py`: the upper case letters, digits and the punctuation of the names, measured with Pillow on `TitilliumWeb-Bold.ttf`, a font file that is not in this repository; the host draws the skin font itself, so kerning and rounding may differ a little). The estimate uses the Bold widths, which are an upper bound of SemiBold. The widest name is "Formant Resonance" with an estimate of 223 pixels at 22 pixels (area 272); a test keeps every name under 95 percent of the area (258 pixels).
- **Measured on the Key 61 (MPC 3.10.1.12): a fixed text label (`Label`, type `Text`) placed on a tab is drawn only if its `Data` handle is bound to a valid parameter**, although ui-reference 6.3 says the handle is ignored for `Text`. With an empty remap nothing is drawn (`showWhenDataModelInvalid` Show and another font style did not help; binding to `Parameter 0` did). So every fixed text of the skin is bound to the parameter of its own control: the names of `85_names.py` and the captions of the radio buttons (the generator's `... seg N` labels, which `85_names.py` binds too). A test fails on a `Text` label with an empty or out of range remap. The style is SemiBold: it was seen to draw on the device, Bold was not tried there.
- **Selectors keep the host header.** The SDK `Slider` (6.1) draws the name of the parameter in upper case over the bar (`GenericLegacy`) and has no key for another text, no way to hide the name and no way to draw the header smaller. A `Label` has no background, so a text over it would stand on top of the host name. The selectors (`sliderWithFocus`, `sliderWithFocusMenu`, the parameters with five or more choices) therefore show the full parameter name as before; this is a limit of the host, not a choice. The full name also stays where the host shows it by itself (the header of the knob and menu overlays).

## Faders and knobs

A continuous (not stepped) control is a knob, except on a Kick page (`docs/kick-pages.json`) whose continuous controls are all levels or mixes (parameter name with level, mix, volume, dry, wet or send): there they are horizontal faders (`faderUni`). The rule is `_is_level_page` in `scripts/gen-mpc-ui.py` and is applied to the Kick page a parameter is taken from (a parameter is placed once). Stepped parameters are unchanged: 2 to 4 choices a toggle or radio group, 5 or more a selector. Before, every parameter with such a word in its name was a fader, so a level among knobs (`Osc 1 Level`) or `Master Volume` on the Macros tab stood alone as a fader.

In the current layout two Kick pages are level pages, so the faders are `Bus 1 Level` and `Bus 2 Level` on the tab `Mixer` (page `mix_bus`, the other controls of the page are switches) and the eight `Chorus Level`, `Compressor Level`, `Delay Level`, `Distortion Level`, `EQ Level`, `Flanger Level`, `Phaser Level` and `Reverb Level` on the tab `FX Level`. Every other level (Osc 1 to 3 Level, Noise Level, Sub Level, Direct Level, Master Volume, the mixes of the effects) is a knob. The Kick pages `mix_sends_osc`, `mix_sends_filter` and `fx_splitter_ms` would be level pages too, they are not on the skin. Tests: `scripts/tests/test_gen_mpc_ui_layout.py` (`test_widgets_follow_the_rules`, `test_faders_only_on_level_pages`, the unit tests of the rule).

## Function keys and sub-tabs

The skin groups its tabs under function keys. Several tabs with the same `fnKeyIndex` and the sub-tab indexes `fnKeySubIndex` 0, 1, 2 ... are sub-tabs of one key; the host steps to the next sub-tab when the key is pressed again, the key shows the `tabName` of the current sub-tab, and `Q-Links.json` has an entry with `Tab` = `fnKeyIndex` + 1 and `SubTab` = `fnKeySubIndex` + 1 for every one of them (observed on the Key 61: sub-tabs work; the SDK allows at most 8 sub-tabs per key and says "at most 32 tabs in total", see below).

- **Layout file**: `scripts/mpc-ui-pages.json` lists the pages (= tabs) in order; `fn` on a page names its function key, the pages of one key follow each other, a page without `fn` is a key of its own. `scripts/gen-mpc-ui.py` checks this (at most 8 per key) and writes the grouping to `skin-meta.json`; the SDK generator still makes one key per page, and `scripts/mpc-skin-extras/95_subtabs.py` (runs last) puts the tabs under their keys, orders the tab list and renumbers `Q-Links.json`. The page of a layout takes one to four Kick pages (`docs/kick-pages.json`) that must fit the 16 slots: every Kick page takes whole rows of four slots (its controls padded to a multiple of 4), so the controls of one Kick page stay together on the Q-Link rows.
- **The committed layout** (`scripts/mpc-ui-pages.json`, `"tabLimit": 34`) has 34 tabs in 10 function keys. Function keys and their sub-tabs, in order: `Macros` (Macros); `Osc` (Osc 1, Osc1 Shp, Osc 2, Osc2 Shp, Osc 3, Osc3 Shp); `Mix` (Sub/Nois, Mixer); `Filter` (Filter 1, Filter 2); `Env` (Env 1 to 4); `LFO` (LFO 1 to 4); `Mod` (Mod 1-2, Mod 3-4, Mod Amt); `FX` (FX Chain, FX Filt, Distort, Comp 1, Comp 2, EQ); `FX 2` (Chorus, Delay, Phaser, FX Level); `Master` (Master, Voice).
- **Measured on the Key 61 (MPC 3.10.1.12): the host loads a skin with 34 tabs in 10 function keys** (also the 32 tab one), so the sub-tabs do not count in the "at most 32 tabs in total" of the SDK (ui-reference 3.5); the sub-tab dots show under the function keys (6 under Osc, 4 under Env, ...). The SDK validator (`tools/validate.py`) still reports `ERROR  TUI.json: 34 tabs; at most 32 are supported`. The build (`scripts/build-mpc.sh`) accepts exactly that one finding, like the `file64` one of a single architecture build (`scripts/tests/test_build_mpc.py`), and fails on every other validator error.
- **The 32 tab fallback** (`scripts/mpc-ui-pages-v32.json`, build it with `--skin-layout`) merges two pairs of tabs: `FX Filt` + `Distort` into `Flt+Dist` (14 controls, both tone shaping stages) and `Comp 2` + `FX Level` into `Cmp2+Lvl` (16 controls: the mid and high band of the compressor and the eight effect levels), placed behind `Comp 1`; `FX` is then FX Chain, Flt+Dist, Comp 1, Cmp2+Lvl, EQ and `FX 2` is Chorus, Delay, Phaser. Every control of every Kick page stays in both layouts (a test compares with the parameters of the skin at `7a0d198` and checks that the layouts hold the same parameters). The validator has no finding for it.
- **SDK tool limit**: `tools/gen_ui.py` refuses more than 32 pages. `scripts/run-gen-ui.py` runs it and lifts that limit only when the ui.json has more pages (34 tab variant); the build uses it for all skins. `scripts/build-mpc.sh --skin-layout FILE` picks the layout file (default `scripts/mpc-ui-pages.json`).

## MPC XL pads

The measurement was done on an MPC XL running MPC OS 3.10.1.12, using a diagnostic build of the plugin with callback statistics and MIDI counters (format 2). The owner pressed the pads by hand because pad input cannot be simulated remotely. The plugin was on a plugin track in the `Sbtest` project.

| | Full Level on | Full Level off |
|---|---|---|
| note on / note off | 19 / 19, channel 1 | 16 / 16, channel 1 |
| note-on velocity | always 127 | varied (96 and 127 seen) |
| poly aftertouch | 0 | 112 messages, values 1..127, one stream per held pad (per note), about one message every 6 milliseconds |
| channel pressure | 0 | 0 |
| pitch bend | 0 | 0 |
| CC (including CC 74) | 0 | 0 |
| channel | 1 | 1 |

What this means: the host passes note, velocity and per-pad pressure (poly aftertouch) to an external plugin; the X/Y position of a pad does not arrive in any form (no pitch bend, no CC 74, no other CC) and there is no MPE channel rotation; with Full Level on neither velocity nor pressure passes.

The host asked `effCanDo` only for `"bypass"` (answer 0) and `"receiveVstMidiEvent"` (answer 1), never for `"MPE"`, and made no `effVendorSpecific` call.

Poly aftertouch drives the modulation source "Poly Aftertouch"; the factory preset "MPE Pressure Lead" routes it to Filter 1 Cutoff and Osc 1 Unison Detune, and on the device pressing harder audibly opened the filter (heard by the owner, not measured).

Not measured: the MPCe Q-Link mode from a drum track to plugin parameters, 16 Levels, Note Repeat, pad lighting from a plugin.

## Pad pressure

The MPC pad sends polyphonic aftertouch for every held pad ("MPC XL pads"). The plugin turns it into an opening of Filter 1 by default, for every preset, without changing what a preset contains:

- **What it does.** The own engine (the engine of the MPC package) adds, per voice, an offset to the Filter 1 cutoff: pressure 0 to 1 of that voice (poly aftertouch value divided by 127) times the amount times 36 semitones, added in the control domain of the cutoff (the same domain the modulation matrix uses, `core/engine-own/voice/voice.cpp`). Only the cutoff of Filter 1: not Filter 2, not the frame, the level, the vibrato or the unison. It comes on top of the knob and of any modulation slot of the patch (if a preset's modulation matrix already contains a route from Poly Aftertouch to Filter 1 Cutoff, such as "MPE Pressure Lead", the layer does not add to that voice, preventing a duplicate effect). The pressure of each voice is smoothed with a one pole filter of 12 milliseconds, so the stream of values the pad sends (about one every 6 milliseconds) moves the cutoff in fine steps and does not make it zipper. A note starts with its first pressure value as it is. The layer is a function of the pad pressure only: the knob, the presets and the saved state of the engine are not written to. It costs nothing while the amount is zero or the switch is off (no smoothing, no addition), and a voice does not leave the envelope cache of the engine for it (`core/engine-own/own_engine.h`, `setOwnPadPressureToCutoff`).
- **Polyphonic vs Channel Aftertouch (0xA0 vs 0xD0).** The layer reacts strictly to polyphonic aftertouch (0xA0, per-voice/per-pad pressure). Channel aftertouch (0xD0), which keyboard instruments such as the MPC Key 61 may send from their keys, is currently ignored by the pad pressure layer; measurement from the designer's test rig is pending, and until then the layer reacts strictly to 0xA0.
- **Two parameters.** "Pad Pressure" (off or on, display "Off" / "On") and "Pad Pressure Amount" (0 to 100 percent, display "35") come after the 32 "Spectrum n" columns: indices 2673 and 2674 (2637 engine parameters, 4 cursors, 32 spectrum columns); in every build except the overlay build they are the last two parameters of the list (the overlay build has "Overlay Instance" after them, see "Parameter order"). Both are automatable and have parameter properties (a switch; a step of 1 percent). No index before them moves. A build without the LFO display has them at 2637 and 2638, one without the spectrum at 2641 and 2642; the skin of `45_pad_pressure.py` refers to the indices of the default build.
- **Parameter order (fixed).** The parameter list of the MPC shell is, in this order: the engine parameters (`docs/params.json`, 2637), 4 "LFO n Cursor" (2637 .. 2640), 32 "Spectrum n" (2641 .. 2672), "Pad Pressure" (2673), "Pad Pressure Amount" (2674), and LAST, only in a build with `SYNTHYBOY_MPC_OVERLAY`, "Overlay Instance" (2675). The indexes of the builds without the overlay never move (the overlay build only adds one parameter at the very end); a build without the LFO display or the spectrum moves the later groups down as described above, and "Overlay Instance" is always the last one. Everything that computes these indexes follows it: `PluginInstance::overlayParamIndex()` and `padPressureBase()` in `shell-mpc/synthyboy_mpc.cpp`, the overlay instance report, `ctx.param_count` of the skin modules (`45_pad_pressure.py`, `40_spectrum.py`, `50_filter_overlay.py`: params.json entries + 4 + 32 [+ 2 for the overlay parameter]), and the host tests (`lfo_live_host`, `spectrum_live_host`, `pad_pressure_host`, `overlay_instance_host`; the first three take the word `overlay`).
- **Pad pressure in the overlay.** The overlay draws the Filter 1 curve from the engine's readout of the modulated cutoff (`copyReadout`, `setReadoutTargets`). The readout of a knob is the value as the voice that sounded last hears it (`Voice::modulatedParam`), and the pad pressure layer adds its offset to exactly that modulation delta, so the displayed cutoff and the curve include the pad pressure contribution of that voice, without changing the sound (the readout only reads; test `pad_pressure_is_in_the_filter_1_cutoff_readout` in `core/tests/test_own_pad_pressure.cpp`). With several held notes the curve shows the voice played last, like for every other modulation. Channel aftertouch (0xD0) is not used by the layer, so it does not move the curve either.
- **Defaults.** On, 35 percent: a full pressure opens the cutoff by about 12.6 semitones, one octave. That is clearly audible on a held pad and does not turn a dark patch into a bright one at the first touch; the player raises it to 100 percent (three octaves) for a stronger effect or lowers it. The default applies when the plugin is created; the settings are not part of a preset, a program change leaves them alone.
- **State.** The two settings are saved in the state chunk as two members at the end of the document (`"mpcPadPressure":1,"mpcPadPressureAmount":35.00`, `shell-mpc/pad_pressure.h`) and restored with it. A chunk without them (a project saved before this feature) leaves the settings as they are. The chunk is the same with and without the display parameters.
- **Full Level must be off.** With the pad's Full Level on, every hit has velocity 127 and the pad sends no pressure at all ("MPC XL pads"), so the layer has nothing to follow. The skin says so beside the controls.
- **Skin.** The Master tab has its bottom row free: `scripts/mpc-skin-extras/45_pad_pressure.py` puts the toggle (Q-Link 1) and the amount knob (Q-Link 2) in its first two columns and a two line text in the third ("Full Level must be off for pressure"); nothing is placed at x 1025 or to the right of it, and the skin keeps its 34 tabs (the validator's one accepted finding stays "34 tabs; at most 32 are supported"). The key and the short names of the two parameters are registered with `ctx.add_param_key` (`scripts/apply-mpc-skin-extras.py`), so `80_layout.py` and `85_names.py` treat them like any other control.

## Output level

The MPC shell passes the engine's output through an output stage (`shell-mpc/output_stage.h`) before it reaches the host:

- a fixed make-up gain, `SYNTHYBOY_MPC_OUTPUT_GAIN_DB` (CMake cache entry of `shell-mpc`, default 6 dB, range -24 .. 24; 0 = no gain);
- a stereo-linked peak limiter behind it with its ceiling 1 dB under full scale: the gain reduction falls at once to what keeps the louder channel at the ceiling (no look-ahead, no latency) and recovers with a time constant of 120 milliseconds. The limiter is always on.

Why: the factory presets are levelled to a four-note chord whose RMS is 20 dB under full scale, with peaks near full scale. On the device that reads as quiet next to the stock instruments, and a preset cannot be raised further without clipping its attack. The gain raises everything; the limiter takes the attacks that would pass full scale.

There is no separate parameter for it: the level control of the instrument is Master Volume (first knob of the second row of the Macros tab), which is saved with the project. The spectrum shows the signal after the output stage, that is what the host gets. The desktop plugin has no output stage.

Tests: `shell-mpc/tests/run_output_stage_test.sh` (the stage alone) and `shell-mpc/tests/output_level_host.cpp` (the plugin against a build with 0 dB: a soft note is louder by the gain, a full chord never passes the ceiling); both run in `shell-mpc/accept.sh`.

## Overlay (experimental)

Live pictures on fourteen tabs, drawn by the plugin itself on a display plane that the MPC firmware does not offer to plugins: the response curve of Filter 1 and Filter 2, the shape of LFO 1 - 4 with the cursor of the playing voice, one cycle of Oscillator 1 - 3, the live phase marker of Envelope 1 - 4 on top of the native envelope widget, and the spectrum of the plugin's output as a curve over the row of meters of the Macros tab. EXPERIMENTAL, off by default; proven on the MPC Key 61 (32-bit) and on the MPC XL (64-bit) with the same code. The skin alone cannot do this: the SDK widgets have no curve that follows the real filter, no LFO shape with modulation and smoothing, no oscillator output with warp and morph (the `Envelope` widget draws broken lines from a few stage values, see "Envelope tabs").

**What it is.** The panel is driven by a display controller with several planes: the whole UI of the application on one (the primary plane), a few the application uses for itself (a cursor, a small sprite) and some that are free and sit above the UI (on the Key 61: UI 33, cursor 35, free 38 and 40, CRTC 37; on the XL: UI 34, an application sprite 40, free 46, 52, 58, 64, 70 and 76, CRTC 82). The plugin lives inside the MPC process, which holds the display device (`/dev/dri/card0` on both) as DRM master. The overlay module (`shell-mpc/overlay/`, compiled in only with the CMake option `SYNTHYBOY_MPC_OVERLAY`, default OFF) finds the CRTC and a free plane at run time ("Discovery") and puts an ARGB picture on that plane over the region of the view whose tab is on screen; the host's own UI keeps working underneath (it still gets every touch). Only one view is visible at a time (one plane), of ONE instance at a time: with several plugin instances (several tracks) the one whose page is on screen is drawn ("Several instances"). Every picture comes from the real DSP code of the engine, not from a drawing of its own: the filter curve from `FilterResponse` (`core/include/synthyboy/filter_response.h`), the LFO shape from `LfoDisplay` (`core/include/synthyboy/lfo_display.h`, the shape function `Voice::lfoValue` calls), the oscillator cycle from `OscCycle` (`core/include/synthyboy/osc_cycle.h`, the oscillator class of the voice), the envelope phase from the engine's readout.

**Views.** A view is a region of a tab, a pair of marker squares and a data source with a draw function (`shell-mpc/overlay/views.h`). They are listed with their numbers in `shell-mpc/overlay/overlay_layout.json`.

- `Filter 1`, `Filter 2` (region at the top of the tab): the response of the filter for the knobs, and for the live (modulated) cutoff and resonance of the voice that sounded last. With nothing playing, macros, the mod wheel and the other sources that have a value without a voice move the readout too (engine: the idle readout); a modulation by an LFO or an envelope needs a voice. A filter that is switched off draws a flat line.
- `LFO 1` - `LFO 4` (the picture region of the tab): the shape as the engine plays it (built-in or custom shape with its point modulation, swing, direction, the phase offset, the trigger type, the smoothing), a smooth line with a fill. The x axis is the time since the note started, in cycles, so the phase offset shifts the picture; a cursor (vertical line and a dot on the curve) runs at the live phase of the voice that sounds, and is hidden when none does. Not drawn: the delay and fade in, the stereo lane (the left lane is shown). The tempo for synced rates is the host's.
- `Osc 1` - `Osc 3` (the wavetable picture region): one cycle of what the oscillator produces for the current settings: the wavetable at the frame position including smooth or stepped reading, the frame remap, warp 1 and 2 and the spectral morph, following the modulated frame, warp amount and morph amount live. The type Wavetable is covered (the built-in tables and the preset table of the content); the types Sample, Granular, Spectral and Multisample have no single cycle: the view shows the empty frame, an oscillator that is off the same. Not in the picture: unison, pan, level, the pitch parameters, the start phase, warps that read another oscillator.
- `Spectrum` (the row of the 32 meters of the Macros tab, 1208 x 136 pixels): the spectrum of the plugin's own output as a smooth filled curve, 256 points on a log axis from 20 Hz to 20 kHz on the dB scale of the meters; the analysis, the drawing and the tests are in "Spectrum" ("The curve over the meters"). The meters stay underneath; the markers and the instance picture are drawn in the 8 pixel gaps between two meters.
- `Env 1` - `Env 4`: the native envelope widget stays visible and editable; a transparent plane over it draws a dot and a soft vertical line at the point of the widget's curve where the playing voice is (stage and progress from the engine's readout). The position comes from the geometry rule of the widget (`shell-mpc/overlay/env_geometry.h`, measured on the device); before a dot is drawn the plugin reads the primary framebuffer under the point and requires the colour of the widget's line (the stage handles hide the line at the corners: there the visible stretches of the polyline are checked instead); a dot that fails the check is not drawn and is counted in the status file. The two marker squares are painted over in the colour of the widget's background; nothing else of the plane is opaque.

**Discovery (nothing of a model is compiled in).** The same code runs on both devices (`shell-mpc/overlay/discovery.h` holds the rules and is tested against the plane tables of both devices, `shell-mpc/overlay/drm_linux.h` reads the display, `shell-mpc/overlay/cpu_plan_linux.h` the cores). It happens when the screen is first read, and everything it finds is in the status file (`display_*`, `cpus_*`, `rotation*`, `pace_*`).

- The display and the CRTC: the application's descriptor is found by scanning `/proc/self/fd` for a link to a `/dev/dri/card*` device that has master rights (`DRM_IOCTL_AUTH_MAGIC` with magic 0 answers EINVAL to a master and EACCES to anybody else) and CRTCs. What is on the display is read through a descriptor of OUR OWN on the same device (universal planes are switched on there, a capability of that descriptor only; the application's descriptor never gets a client capability): the primary plane that is on a CRTC with a valid mode and shows a framebuffer is the application's UI plane, its CRTC is ours. A driver that reports no plane types: the CRTC with a mode and a framebuffer, and the plane that shows it.
- The overlay plane: free (no CRTC, no framebuffer), possible on that CRTC, offers ARGB8888, not a cursor plane, and stacking above every plane the application has on the CRTC (the `zpos` property when the driver has it; an overlay type plane stacks above the primary one by the hardware order otherwise). The lowest numbered one is used, the others are spares. The plane is checked through its reported state (`GETPLANE`: our CRTC and a framebuffer; the GPU helper also checks that the framebuffer is its own, once a second, right after an update): when another program takes the plane, or an update of it fails, the module drops what is its own WITHOUT switching that plane off (it is not ours any more), moves to the next spare and shows the picture there; with no spare left it disables itself with the reason. A plane that is found switched off (no CRTC and no framebuffer: a mode set of the application switches off every plane it does not name) is not taken but set again on the same plane (`display_plane_refreshes`), and a failure while the CRTC has no mode (the display is off) moves nothing. The helper also checks a picture that stays on the plane (once a second), so that a plane taken between two updates is found as well.
- The panel size comes from the mode of the CRTC. The real refresh period is measured from the time stamps of forty consecutive vblanks (the number in the mode is wrong on the XL); the vblank is waited for with `DRM_IOCTL_WAIT_VBLANK` on the pipe of the CRTC (its index in the resource list).
- The rotation of the UI on the panel needs no table: the skin draws marker squares of colours that no other view uses (see "How it knows its page is on screen"), and the marker pair of the view on screen is looked for in the primary framebuffer under each of the four rotations (90, 270, 0 and 180 degrees); exactly one rotation may match, otherwise nothing is decided (`rotation: unknown`, `hidden: rotation ambiguous`) and the next check tries again. The result is kept for the life of the process (`rotation_source: found from the markers`). The file `/tmp/synthyboy-overlay-rot` (0, 90, 180 or 270) overrides it; removing the file brings the found one back.
- The cores: the overlay thread and the helper stay off the cores the kernel isolates (`/sys/devices/system/cpu/isolated`) and off the cores the audio threads of the application are pinned to (the threads whose name contains "audio", from `/proc/self/task/*/status`, when their affinity is narrower than the online set); re-read every ten seconds, the helper is set again when the cores change. The isolated cores are never used; the audio threads' cores are taken out only as long as other cores are left: the Key 61 pins AudioWorker0 to AudioWorker3 to its four cores, so there only the isolated cores 2 and 3 are kept off and the overlay shares 0 and 1 with the audio threads, while on the XL (AudioWorker0 to 3 on the cores 4 to 7) it runs on 0 to 3. When even that leaves nothing, nothing is changed.
- The GPU: the helper tries every `/dev/dri/renderD*` (the GPU drivers first, then the others; `SYNTHYBOY_OVERLAY_RENDER_NODE` names one first) until one gives a GBM device, an EGL display and an ES2 ARGB8888 configuration, and opens `libEGL`, `libgbm` and `libGLESv2` by their sonames, then their plain names, then the usual library directories (`SYNTHYBOY_OVERLAY_GL_DIR` first); the error lists what was tried.

**Pacing.** A plane update through the legacy call `SETPLANE` waits for the vblank (the thread that makes it is never the audio thread). The MPC XL panel really refreshes at a rate other than its mode says, and its plane update is not a fixed one vblank per picture: while the application's own UI is moving (it commits a frame of its own on the same CRTC at every vblank: a knob dragged, a page with live meters) updates called back to back alternate between waiting one and two vblanks (uneven pictures), and a call made a few milliseconds after a vblank gets the next vblank only part of the time, the later the less often. With a static page on the screen the same calls are exactly one vblank each, so what decides is the competition with the application's commits for the display's locks, which a blocking update holds while it waits. A call made the moment a vblank wait returns (nothing sleeping in between) is taken for the very next vblank in both cases, and with one call on every second vblank the intervals between the pictures are exactly two vblanks. So the pace is a GRID: the stride is the whole number of vblanks nearest to a thirtieth of a second (two on both devices: 30 pictures a second on a 60 Hz panel, a little over 28 on the XL), the helper (`shell-mpc/overlay/vblank_pacer.h`, `shell-mpc/overlay/vblank_linux.h`) draws just early enough, waits for the vblank counter of the next slot of the grid and calls `SETPLANE` at once; a picture that is late takes the next slot of the same grid; after a pause a new grid starts at the next vblank; where no vblank can be waited for a timer of a thirtieth of a second paces (`pace_mode: timer`). The CPU drawing does the same inside its plane update. Tried and not adopted (the measurements are in "Known host behaviour"): back-to-back updates, updates after a delay of a few milliseconds, the update from a thread other than the one that waits for the vblank, an update with the same framebuffer or a one pixel move, and the non-blocking atomic update of the plane only: the application's descriptor does have the atomic capability (an empty test-only request is accepted, which sets nothing), the non-blocking update returns at once, but when it reaches the screen cannot be measured without a completion event, and such an event would go into the application's own event queue; so the proven legacy path stays. Because the update holds the display's modeset locks while it waits, any other call that needs them (reading the CRTC, `GETPLANE`) waits too: the overlay thread therefore hands over the next scene FIRST in every step and schedules its steps from the start of the previous one, and the plugin leaves the checking of the plane to the helper while the helper draws.

**Build.** The overlay needs a skin made for it (the curve area, two marker pictures, the controls re-arranged), so the package is built with both: `scripts/build-mpc.sh --arch all --cmake-arg -DSYNTHYBOY_MPC_OVERLAY=ON --skin-layout scripts/overlay-skin/mpc-ui-pages-overlay.json` (both architectures in one package: the plugin and the GPU helper of each, `VST/synthyboy-overlay-gpu-arm32` and `VST/synthyboy-overlay-gpu-arm64`; the default build and the default skin are untouched; with the option OFF the plugin is byte for byte the one without the module, `shell-mpc/accept.sh` compares the binaries). Against the main line (`origin/develop` `f88e533`, merged 2026-11-14) the production package is identical in everything but the plugin binary: the skin is byte for byte the same (checked by building both with `scripts/build-mpc.sh --arch arm32` in the same image and comparing the `Plugin Skins` folders; `scripts/tests/test_mpc_skin_overlay.py` keeps the production skin equal to the one the modules without the overlay module make), the package files the same. The arm32 plugin binary is NOT byte for byte the one of `origin/develop`, and cannot be with the overlay branch's engine: the display additions of the own engine are compiled in whether or not the overlay is on (the readout of an idle engine with the source mask of the modulation matrix, the finer envelope stages in `LiveValues`, the filter set-up shared with `FilterResponse`, the LFO display code), so five objects differ (`own_engine`, `voice`, `mod_matrix`, `fx_modules`, `synthyboy_mpc`; the last one only by the stack frame, `LiveValues` is 48 bytes larger). The sound is not changed (the core test suite passes on the merged state); making the binary identical would need these engine additions behind a compile switch, which they do not have. The numbers shared by the skin and the plugin (region of every view, marker squares and their colours, and `meterRow`, the geometry of the row of the 32 meters that `scripts/mpc-skin-extras/40_spectrum.py` reads and whose bounding box is the region of the `spectrum` view: `scripts/gen-overlay-layout-header.py` and `scripts/tests/test_mpc_skin_overlay.py` check that they agree) are in one file, `shell-mpc/overlay/overlay_layout.json`; `scripts/gen-overlay-layout-header.py` makes `shell-mpc/overlay/overlay_layout.h` of it and a test checks that the header is current.

**The skin variant.** `scripts/overlay-skin/mpc-ui-pages-overlay.json` (`"variant": "overlay"`) is the production layout with two more pages: `Filter 1` and `Filter 2` (curve area at the top, below it two rows of four controls: On, Model, Style, Drive and Cutoff, Resonance, Mix, Key Tracking; Q-Link map and frames match the two rows) with the sub-tabs `F1 Model` and `F2 Model` (Blend, Comb Blend Offset, Formant X, Y, Resonance, Spread, Transpose) under the same function key: 36 tabs, so every control of the production tabs is still reachable. The extras module `scripts/mpc-skin-extras/50_filter_overlay.py` does the work and does nothing unless `skin-meta.json` names that variant, so the production skin stays as it was (`scripts/tests/test_mpc_skin_overlay.py` compares it byte for byte with a build without the module). The Macros tab is the production tab plus the two marker squares and the instance picture of the `spectrum` view, in the gaps between two of the 32 meters, which stay as they are. The LFO, Osc and Env tabs are the production tabs plus the two marker squares of their view on top of the existing pictures: the shape and wavetable pictures and the native envelope stay where they are and are what the player sees when the overlay is off or disabled. `scripts/build-mpc.sh` accepts the one validator finding about the number of tabs of the layout it builds (36 here, 34 for the default; any other count is still an error).

**How it knows its page is on screen.** The host does not tell a plugin which page is visible. The skin draws two small solid squares inside the region of every view, near its two ends, in colours that no other view uses (the markers: the colour pair says WHICH view is on screen, so the plugin needs no knowledge of tab names; the numbers in the JSON are checked against each other: no two marker colours are within the detector's tolerance). Ten times a second the plugin reads the pixels of the marker pairs of all views from the application's primary framebuffer (GETCRTC, GETFB2, dma-buf export, read only mapping on a descriptor of its own, the mappings cached by the identity of the buffer); both markers of a view present (within 2 in every colour channel at four corner samples and the centre) means that view's tab is on screen and not covered. The overlay is on another plane, so the markers stay readable while it covers them; the overlay's picture covers them (an opaque view has a dark background of its own over the whole region; the transparent envelope view paints only its two squares), so the player never sees them. A popup, a menu or another tab replaces or covers the markers and the overlay goes within one check.

**Several instances (which instance's page is on screen).** The host does not tell a plugin whose page is visible, so the SKIN does. Every plugin instance owns a SLOT, 0 to 15: the lowest free one is given out when the instance is created (`VSTPluginMain`) and kept until it closes (`effClose`); a slot is reused only after its instance closed, and no two live instances share one (`shell-mpc/overlay/instance_slots.h`, the table is in the controller under its lock). The slot is exposed as one more display-only parameter, "Overlay Instance": the LAST parameter of the list, after the two pad pressure parameters (index: engine parameters + 4 LFO cursors + 32 spectrum columns + 2 pad pressure parameters = 2675 in the default overlay build; "Parameter order" in the section "Pad pressure"), only in a build with `SYNTHYBOY_MPC_OVERLAY`, not automatable, not in the state chunk, writes ignored. Its value is the frame number of a film strip divided by 32 (a multiple of 1/32 is exact in a float, so the host's choice of frame cannot round to the neighbour): frame 0 is blank (nothing reported yet), frames 1 to 16 are the slots 0 to 15, frame 17 is "none" (an instance beyond the sixteenth), the rest is blank. The skin places on every tab with a view a tiny film strip `Image` (33 frames, 6 x 6 pixels, on the envelope tabs 4 x 4) bound to that parameter next to the two markers, inside the region of the view; every frame is one exact colour of the table in `shell-mpc/overlay/overlay_layout.json` (`instance`; the PNG settings are those of the marker pictures, and the colours are checked against every marker colour, the background and each other). The host draws the frame of THIS instance's value, so the colour the page detector reads from the primary framebuffer says which instance the page on screen belongs to; the overlay thread then reads the parameters and the live values of that instance only. The overlay is visible when the markers of a view match AND the instance picture has one of the 16 slot colours (all five sample pixels) AND that slot is alive; every other case is hidden, with the reason in the status file (`hidden: instance of the page not identified`, `hidden: instance slot N is not alive`, `hidden: instance has no slot (more than 16 instances)`, `hidden: instance closed`). The view objects keep cached data (curves, history, smoothing), so a view that last showed another instance is made new before it reads the new one. The instance picture is covered by the overlay like the markers (the dark picture of an opaque view, a painted square on the envelope views).

- Reports. The display thread reports the parameter with `audioMasterAutomate` once after the instance is created, when its value changes, and whenever the overlay thread asks (`IInstanceView::requestOverlayReport`, which only sets a flag; the call to the host is the display thread's, never the audio thread's and never the overlay thread's). The overlay thread asks all live instances when the markers of a view are on screen but the instance picture shows no valid colour (the host has not drawn it yet, or shows a stale frame until the parameter is reported): at once for the first time, then at gaps that start at 0.4 seconds and double up to 3.2 seconds while no valid colour is read, and the overlay stays hidden until one is read. A valid colour of a slot nobody holds, and the none colour, ask for nothing (the answer is complete). Pages without markers ask for nothing.
- More than 16 instances: the instances beyond the sixteenth get no slot (their parameter says "none"); they never show the overlay, and they do not take a slot from the others. The slot of an instance is assigned at creation and does not change when another instance closes.
- A frame number that is not a slot colour (a blank frame, a colour that belongs to no slot, one of five sample pixels differing) is never taken for a slot.
- Debug: while `/tmp/synthyboy-overlay-fake-slot` exists the plugin reports the slot named in it instead of its own: a number (0 to 15 is that slot, any other number the "none" frame), `none`, `blank` (frame 0), or `stale` (frame 0 until the overlay thread asks for a report, the real slot after that: what a host looks like that shows an old picture until the parameter is reported). It is read by the display thread once a second and at every report, and meant to show on a device with ONE instance that the host redraws the picture with the other colours and that the overlay hides when the colour belongs to a slot that is not alive; remove the file to get the real slot back.

**Threads and cost.** One thread for the whole process (`sb-overlay`, same scheduling as the display thread: `shell-mpc/thread_policy.h`, plus the cores of the audio threads and the cores the kernel isolates are taken out of its affinity, "Discovery"). The audio thread does nothing for it. The CPU drawing (the fallback; "GPU drawing in a helper process" below is the other renderer) makes 30 pictures a second while the curve changes and none while nothing changes (the plane keeps showing the last buffer); with the helper this thread only computes the data and hands scenes over. A full computation of the curve costs several milliseconds on the device, so the full computations are limited to a share of one core; between two of them, when only the cutoff moved, the last exact curve is translated along the logarithmic frequency axis and the exact one follows as soon as the budget allows, so the picture is exact again when the motion stops. The measured numbers are in "Known host behaviour", "Observed on the device".

**GPU drawing in a helper process.** With the build option `SYNTHYBOY_MPC_OVERLAY_GPU` (CMake: `AUTO` by default = on for an ARM cross build with `SYNTHYBOY_MPC_OVERLAY` ON, `ON` / `OFF` force it) the pictures are drawn by the GPU of the device (the Key 61: Mali-T760, the XL: Mali-G610, both Mesa panfrost, OpenGL ES 2) instead of the CPU, in a SEPARATE PROCESS: a crash or a driver fault of the helper must not take the MPC application down, and Mesa's libraries are not loaded into the application. The CPU drawing stays in the plugin as the automatic fallback; with the helper missing, failing or switched off the behaviour is exactly the one described above.

- The helper is the executable `synthyboy-overlay-gpu-arm32` (`synthyboy-overlay-gpu-arm64` for the 64 bit build) in `VST/` next to the plugin binary; the plugin finds it relative to its own path (`dladdr`, `shell-mpc/overlay/service.h`). `scripts/build-mpc.sh` puts the helper of every architecture it built into the package when the target exists (overlay build on ARM, `--arch all` gives both); the production package has none, so it is unchanged byte for byte. Source: `shell-mpc/overlay/gpu-helper/` (`main.cpp`, `gl_api.h`, its own `CMakeLists.txt`), built by `scripts/mpc-container-build.sh` with the same ELF checks as the plugin (libc only, glibc symbols up to the ceiling of the device of that architecture: 2.39 on the Key 61 and on the XL, read from `/lib/libc.so.6` of both; no Mesa library in the dynamic section). A build host of the target's own architecture (Docker on an arm64 computer building arm64) has no DRM uapi headers in its native `linux-libc-dev`: the container script then copies them from Debian's armhf cross package (they do not depend on the architecture).
- Build without the device's libraries: the build image has no Mesa headers or libraries and the repository carries no device binary. `gl_api.h` declares the few EGL / GLES2 / GBM entry points it needs (stable ABIs: Khronos values, Mesa's `gbm.h`) and finds them with `dlopen` / `dlsym` of `libEGL.so.1`, `libgbm.so.1` and `libGLESv2.so.2` at run time. So the helper links against libc only, the build needs nothing but the cross compiler (reproducible from the repository alone), and a missing library or function is a clean `error` message to the plugin and the CPU path, not a crash at start. The rendering device is a render node found at run time ("Discovery"); the libraries are searched by name and in the usual directories.
- Start: the overlay thread starts the helper the first time a view is on screen (never earlier), with `posix_spawn` (no `fork` without `exec` in this multi-threaded real-time process: only the spawning overlay thread waits for the `exec`). The child gets its socket on descriptor 3, `/dev/null` and the log file `/tmp/synthyboy-overlay-gpu.log` as 0 - 2, every other descriptor of the application is closed (`addclosefrom_np`), an empty signal mask and default handlers. Scheduling and affinity are the overlay thread's (SCHED_OTHER, nice 0, never the isolated audio cores). The first picture is drawn by the CPU; when the helper has said it is ready the pictures move to the GPU.
- Channels (`shell-mpc/overlay/gpu/scene.h`, one header for both sides, `kProtocolVersion` 3; version 2 added the second colour of an op, the op `kOpFillGradient` (a fill coloured by a vertical gradient) and the scene kind `kKindSpectrum`, version 3 the vblank pipe, the stride and the measured period in the hello, the helper's statistics of the presentation intervals in the shared block, and the rotations 0 and 180; the plugin and the helper are shipped together, and a helper of another version answers the hello with an error message (`protocol version mismatch`), so the plugin counts a failure and draws with the CPU, never a misdrawn picture): a `SOCK_SEQPACKET` Unix socket pair with fixed 64 byte messages, and a shared block (memfd, mapped by both). The `hello` carries two descriptors with `SCM_RIGHTS`: the application's own DRM descriptor (the same open file description, so the helper has the application's master rights on plane 38; checked on the device before anything was built) and the memfd. Messages from the plugin: hello, show (region, plane position, rotation, view name), scene (a kick with the sequence number), hide, quit. From the helper: ready (GL renderer, start-up time), shown, frame (frames presented, the scene sequence number, render and SETPLANE times, skipped vblanks, late SETPLANE calls), hidden, error (text).
- The scene is a display list in canvas pixels of the landscape region (`SceneData`: clear, rectangle, vertical line, disc, and one polyline of up to 512 row values used by `fill`, the gradient fill and `stroke`), written by the plugin under a seqlock, so the helper never reads a half written scene. Every view describes itself (`IView::describe`): the geometry, order and colours are those of the CPU drawing; `shell-mpc/overlay/tests/gpu_scene_host.cpp` interprets the scene of every view type with the CPU drawing helpers and compares it with the CPU picture. The helper does everything GPU: GBM surface (ARGB8888, scanout and rendering) of the panel's portrait size, shaders for the feathered 4 pixel line, the translucent fill, the grid, the discs, the rotation in the vertex shader, `glFinish`, then the finished buffer object goes to the plane without a copy (dma-buf, `PRIME_FD_TO_HANDLE` on the shared descriptor, `ADDFB2` cached per buffer object, legacy `SETPLANE`, which waits for the vblank). The scene changes at most 30 times a second; the helper draws only when the plugin kicks it and sleeps otherwise.
- Clean-up: on hide, quit, a closed socket (the plugin or the application went away) or SIGTERM the helper takes the plane off, removes its framebuffers, closes its GEM handles and destroys the surface. Every DRM object it makes on the shared descriptor is entered in a ledger in the shared block: those objects belong to the application's file description and would otherwise outlive a killed helper, so the plugin removes what is left in the ledger itself.
- Health (`shell-mpc/overlay/gpu/gpu_overlay.h`, tested with a fake helper in `gpu_backend_host.cpp`): `idle` -> `starting` -> `running`; a failure (the channel closed or the process gone, an `error` message, no `ready` within 3 seconds, a scene without a frame acknowledgement for 0.7 seconds, a hide without `hidden` for 0.7 seconds) kills and reaps the helper FIRST, then takes plane 38 off (only when the helper had been told to show, or had objects in the ledger: a helper that failed before that leaves the plane to the CPU picture that may be on it) and removes the ledger's framebuffers and handles through the plugin's own descriptor, then the CPU draws within one tick (`renderer: cpu`). The helper is started again after 1, 2 and 4 seconds (`backoff`); the fourth failure keeps the CPU for the life of the process (`exhausted`); a helper that ran five minutes without a failure gets its failure count back to zero. A planned stop (the file switch, closing) is no failure.
- Switches: `/tmp/synthyboy-overlay-nogpu` (exists = CPU drawing, the helper is stopped; checked once a second, switches live in both directions). Debug: `/tmp/synthyboy-overlay-gpu-dump` makes the helper read back its finished frame (`glReadPixels`, rows bottom up, RGBA premultiplied) once a second into `/tmp/synthyboy-overlay-gpu-frame.raw` with the numbers in `/tmp/synthyboy-overlay-gpu-frame.txt`.
- The status file says who draws: `renderer: gpu` or `cpu` (the helper is running and acknowledged, and the last picture was its), `gpu_state` (`idle`, `starting`, `running`, `backoff`, `exhausted`, `off` = the file switch, `not built`), `gpu_helper_pid`, `gpu_helper_starts`, `gpu_helper_restarts`, `gpu_failures`, `gpu_last_error`, the helper's own counters (`gpu_helper_frames`, `_render_ms`, `_setplane_ms`, `_skipped_vblanks`, `_late_setplanes`, `_startup_ms`) and `gpu_renderer` (the GL renderer string). A change of the renderer is written at once, not at the next second.

**Switches and files** (all in `/tmp` of the device):

- `/tmp/synthyboy-overlay-off`: while this file exists the overlay stays hidden (read once a second; removing the file brings it back). `touch /tmp/synthyboy-overlay-off`.
- `/tmp/synthyboy-overlay-nogpu`: while this file exists the CPU draws and no helper runs (see "GPU drawing in a helper process"); removing it brings the GPU back.
- `/tmp/synthyboy-overlay-fake-slot`: debug, see "Several instances": the slot (or `none`, `blank`) the plugin reports for "Overlay Instance" instead of its real one.
- `/tmp/synthyboy-overlay-rot`: `0`, `90`, `180` or `270`, read once a second: overrides the rotation of the landscape UI on the panel that the overlay finds itself ("Discovery"; 90 on the Key 61, 270 on the XL). The same function places the plane, rotates the picture and finds the marker pixels.
- `/tmp/synthyboy-overlay-status.txt`: rewritten once a second (temporary file and rename): the state (`visible`, `hidden: <reason>`, `disabled: <reason>`) and the NAME OF THE VISIBLE VIEW (`view: lfo2`), the rotation, the number of instances (`instances`, `instances_with_slot`, `instance_slots_alive` as a bit mask, `instance_slot` shown, `instance_pixel_read` = the colour read, `instance_slot_read`, `instance_rereports` = how often the instances were asked to report again), the pictures in the last second, the render, rotate and SETPLANE times, the CPU share of the overlay thread, the numbers of the visible view (filter: last computation, live cutoff and resonance, hash of the curve; LFO: shape hash, cursor position; oscillator: kind, cycle hash, live frame and warp amounts; envelope: stage, dot position, the counters of the line colour check), a counter line for every view (`view_<name>: updates, changes, recomputes, frames`), the marker values read for every view, the panel size and the plane rectangle. The discovery: `rotation` (`unknown` until found), `rotation_source`, `display_device`, `display_crtc`, `display_primary_plane`, `display_app_planes`, `display_overlay_candidates`, `display_overlay_plane`, `display_plane_switches`, `display_plane_state`, `display_plane_losses`, `display_mode_refresh_hz` (what the mode says) and `display_refresh_hz` / `display_vblank_period_ms` (measured, `display_vblank_measured`), `pace_stride_vblanks`, `pace_mode` (`vblank grid` or `timer`), `discovery_ms`, `cpus_online`, `cpus_isolated_by_kernel`, `cpus_overlay_allowed`, `cpus_avoided`, `cpus_overlay_thread_now`, `cpus_helper_now`, `cpus_audio_threads`; and the pace: `pace_renderer`, `pace_intervals`, `pace_interval_vblanks` and `pace_interval_ms` (the intervals between two plane updates of one run, counted in vblanks and in buckets of two milliseconds: when the pace is even one bucket holds nearly all of them), `overlay_tick_max_ms_last_second`, `overlay_scene_gap_max_ms_last_second` (the longest step of the overlay thread and the longest gap between two scenes in the last second).
- `/tmp/synthyboy-overlay-dump`: while this file exists, `/tmp/synthyboy-overlay-curve.txt` is rewritten once a second with the data of the visible view: the 256 values of the shown and of the exact filter curve, the 300 values of an LFO shape, the 512 values of an oscillator cycle, the geometry of an envelope (a debugging aid; `synthyboy_filter_response --set KEY=VALUE` computes the same filter curve on a computer).

**Limits and what happens on failure.**

- The GPU helper needs the firmware's own Mesa libraries (`libEGL.so.1`, `libgbm.so.1`, `libGLESv2.so.2`) and a render node; it was made for the Key 61 and proven on the Key 61 and the MPC XL. When anything about it is missing or fails the plugin draws with the CPU, as without the helper (see "GPU drawing in a helper process"). Mesa wants a writable shader cache directory: `/root/.cache` is read-only on the device, Mesa prints one line to `/tmp/synthyboy-overlay-gpu.log` and runs without the cache (harmless: the shaders are small).
- It uses a display plane that is not part of the plugin SDK. A firmware update, or the MPC app itself using the plane, can break it. The plugin checks that the plane is free (no CRTC, no framebuffer) and offers ARGB, takes the next free one when it is not or when another program takes it later, and does not start when there is none.
- The module disables itself for the life of the process, and writes the reason to the status file once, when the descriptor of the display is not found, no free plane is left, or a call to the display driver fails that no spare plane helps (no retry). The plugin then works as without it (the skin without a curve: the dark area stays).
- Several instances: up to 16 (slots 0 to 15, see "Several instances"); the instances beyond them never show the overlay. The overlay is one process-wide singleton; with a skin that has no instance pictures (any other than the overlay skin) or a plugin whose parameter list lacks "Overlay Instance" nothing identifies the instance and the overlay stays hidden. Verified on the device with ONE instance only: the host's redraw with the colours of other slots (debug file) and the hiding for a slot that is not alive are measured there ("Observed on the device"); that the curve follows the track with two real tracks is shown by the Mac tests with fakes only, the test with two real tracks on a device is still open.
- A crash of the MPC app leaves the plane and its buffers to the kernel (they are freed with the app's descriptor). The module removes the plane, the framebuffers and the buffers when the page goes, when the plugin is closed (`effClose`) and from an exit handler.
- It never sets client capabilities on the application's descriptor, never touches the application's planes, never sets a mode and never commits atomically (the one atomic request of the investigation was an EMPTY test-only request in a measuring tool, not in the plugin); only the legacy plane call (`SETPLANE`) on the overlay plane, which waits for the vblank (so it runs on its own thread, never the audio thread).
- Tested on the Key 61 (firmware 3.10.1.12) and on the MPC XL (another panel, SoC and display controller; the firmware version is not recorded here). Other MPC models are not tested. What a human eye has to judge (orientation of the picture, smoothness, the blending, the exact place on the glass) is not in any test.
