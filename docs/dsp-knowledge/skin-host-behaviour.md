# Host behaviour of skins seen on the devices (measured 2026-11-27)

Facts about how the MPC host treats our skin, each with its evidence. Raw files: `/Users/szabi/Documents/Projects/Safian/.hw-local/mpc-perf/host-skin-findings-2026-11-27/`. FACT = measured on a device, SDK = official SDK doc, HYPOTHESIS = not proven. Ask the mpc-expert first; test on a device only for what this page and the SDK do not answer, and write the result here.

## Host list (MenuOverlay) selection and closing
- FACT (Key 61, 2026-11-27): a left-drawer list opened by a native selector (`Show Overlay` on `Mouse Down`/`Enter Pressed`): a row tap only moves the host check mark; the tap on the list header (upper left, about (106,49)) applies the choice and closes. A tap outside does not close. Evidence: `list-probe-results/none-*`.
- FACT: the skin action triggers are only `Mouse Down`, `Double Click`, `Enter Pressed` (SDK `ui-reference.md` section on onAction); there is no `Mouse Up`, so the order of a choice write and a `Focus Lost` cannot be controlled.
- FACT (Key 61 probes A and B): a `Mouse Down -> Focus Lost` action on every row's Choose component (A) or on the overlay component's own actions (B) closes the list on one row tap, but the selection is NOT applied (the selector and the panel keep the old value). Evidence: `list-probe-results/A-*`, `B-*`. Select-and-close is therefore not possible with the stock MenuOverlay.
- Decision: lists keep the factory behaviour (row marks, header applies). Names only, no custom row badges.

## Host list: who draws the names (2026-11-28)
- FACT (Key 61, the list probe of 2026-11-27, `list-probe-results/none-1open-host.png` in the raw folder above): the PLAY OSC list shows the rows "Sub", "Oscillator A", "Oscillator B", "Oscillator C", "Noise". These are the texts of our own `Label` components inside the overlay definition `oscNativeSourceChoices` (skin/defs_play.json; deleted 2026-11-28 when the Play lists moved to the plugin list); the `replacementStrings` entry of the same parameter says "Osc A" .. "Osc C", which does not appear. The host draws the left drawer, the header (the parameter name) and the check mark of the current row; the item names come only from the definition's own rows.
- FACT (community, measured 2026-09-24 on a device, open-mpc `docs/NOTES.md` "Native picker (menu overlay): not available to VST2"; `docs/SDK-PORTING.md`): the native `MenuOverlay` / `ComboBox` opens EMPTY for an external VST2 parameter, also with `replacementStrings` and with a `.vstxml`. The SDK text (`ui-reference.md` 3.3, 6.11: "a full-screen list of the parameter's choices") is wrong for a third-party plugin.
- Consequence: a host list would need one row per option inside the overlay definition (a `Label` with the name and a radio `Button`, handle Data, buttonId k, numButtonsInGroup N, Instant, at y 110 + 80 k, 80 px high, x 0..426; room for 8 rows). A bare MenuOverlay shows an empty drawer. Whether the host scrolls more than 8 rows is NOT measured.
- Owner decision 2026-11-28: lists do not use the host MenuOverlay at all (its row tap only marks, the header applies); every list is the plugin's paged native list, one tap chooses and closes (AGENTS.md "Lists: one tap chooses and closes"). The facts above stay as the reason.

## Lists of dynamic names (file browsers, source of a new modulation), decision 2026-11-28
- The stock MenuOverlay shows no item names of its own for our plugin (see "Host list: who draws the names" above), so a list of file or table names cannot use it: its rows would have to be fixed skin components. The oscillator browsers and the source list of a new modulation therefore use the cells of the modulation picker (stock Buttons and Value Labels, seven rows a page, BACK / UP or GROUPS / PREVIOUS / NEXT); the names are the display text of the row parameters (the host re-reads the text when the cell code changes). Not yet measured on a device.

- FACT (XL, Key 61, 2026-11-27): a skin that differed from a working one only in the Mixer strip labels (a `value` Label of `mixerDestination56` became the shared type `sharedNativeLabel459` with `showWhenDataModelInvalid` "Hide" -> "Show", plus changed Mixer tab text styles) froze the XL project load at the progress dialog "Loading Track Outputs 31/32" (18 %, identical frames 15 s apart; `xl-project-load-freeze-progress-18pct.png`) and the Key 61 rebooted (uptime 1 min after the install). ## Tab background
- SDK `ui-reference.md` 4.3 `backgroundData`: the `colour` is filled first, the `image` (if any) is drawn over it; `colour: "0", image: ""` is transparent; a tab root normally sets an explicit colour. A plain colour needs no bitmap.
- FACT: our skin used one shared bitmap `overlay_canvas.png` (3 292 B on disk, 1280x628 decoded = 3.2 MB RGBA in the host) as the root background of all tabs, with the fallback colour `ff1e1d1e`, while the visible ground is `#090d19`. FACT (Key 61, 2026-11-27, adcfaa5b-based skin): `colour ff090d19` with an empty image on the tabs Env 1 and Mix gives exactly the same ground (9,13,25) as the bitmap tabs (Osc A, Play); the project loads normally, the overlay page detection still reads the markers (`view: env1`, `host_background: on (sentinel read)`), no black areas. A plain colour replaces the bitmap (saves the 3.2 MB decoded background). Evidence: `exp-bg-k61/` photos (copied to the raw folder).
- DONE (2026-11-27): every tab of the overlay skin now has `colour ff090d19` and an empty image (`skin/TUI.json`); `overlay_canvas.png` is deleted. Skin-only generation before/after: the 468 component definitions are identical and only `backgroundData` differs, on all 37 tabs. The sentinel pictures stay (page detection).

## importFiles: splitting the skin into files (expert research 2026-11-28; device measurement Key 61 2026-11-28 below)

Question: can `TUI.json` be split into one file per screen / component definition, joined by the host's `pageData.componentDefinitions.importFiles`? SDK = official SDK doc (active SDK febd2ca, byte-equal ui-reference to upstream e78bad5 per `sources/runtime-sdk-docs/`); DEVICE = factory file read on the XL; all paths under `/Users/szabi/Documents/Projects/Safian/.hw-local/mpc-knowledge/` (KB) unless noted.

- SDK, path rule: `componentDefinitions.version` 2 resolves `importFiles` relative to the folder of the file that holds the list; version 1 relative to an internal MPC folder (`docs-official/mpc-sdk/docs/ui-reference.md:300-301`). Our skin is version 2 (`skin/TUI.json`, checked 2026-11-28).
- DEVICE (XL, 3.10.1): stock skins import with relative `../../` paths: `../../Generic/Generic Knob Overlay.json`, `../../Generic/Generic Menu Overlay.json` (Fabric XL, OPx-4, Qubiq Sub Factory/Visual EQ4/Multiband Filterbank: `private-do-not-publish/reference-skins/*.TUI.json`, `/pageData/componentDefinitions/importFiles`), `../../AIR Components/AIR Generic Components.json` (AIR Reverb Pro), `../../AKAI Components/AKAI Generic Components.json` (LP Filter Sweep, `research_notes/Gyári MPC poti színezés ellenőrzése/theme-and-wrappers.md:45`), `../../Generic/Generic Slider.json`, `Generic Text Overlay.json` (`findings/xl-midi-TUI.json`). From `<Synths>/<plugin>/Plugin Skins/` the `../../` is the `Synths` folder, so FACT: relative resolution against the importing file's folder works on the device for factory skins.
- Absolute paths: the community tools (`docs-community/open-mpc/tools/shadow_skin.py:1553`, `test_make_skinset.py:27`) write `/usr/share/Akai/Content/Synths/Generic/Generic Knob Overlay.json`; the community note says "resolve relative to the skin; use absolute `/usr/share/Akai/Content/Synths/...` paths when the skin lives elsewhere" (`docs-community/open-mpc/docs/NOTES.md:50-51`). Absolute paths are therefore a community-written, not hardware-proven, form for third-party plugins.
- No third-party or community skin that imports a file from its OWN skin folder was found (all community/example skins use `"importFiles": []`: `sources/mpc-vst-dx7/skins/TUI.json`, `examples/d-sdk-plugin-ui-tui-minimalis.md:86`, SDK `tools/gen_ui.py:694`, SDK examples). `theme-and-wrappers.md:46,79` states importing from a third-party plugin was never tried on hardware. HYPOTHESIS (not measured): a plugin folder under `/nvme/VST2 Plugins/<plugin>/Plugin Skins/` (XL) or `/sdcard/VST2 Plugins/<plugin>/Plugin Skins/` (Key 61; `scripts/install-mpc-package.sh:13,21`) resolves `defs/x.json` in the same way as a factory skin. The only SDK statement is the generic rule above.
- Content of an imported file: components only (`localComponentDefinitions`); there is no `tabs`, `replacementStrings` or `info` in an imported file (SDK 3.2: "same shape as `componentDefinitions`"; `pageData.tabs`, `replacementStrings`, `info` are `pageData` keys, ui-reference.md:278-283). FACT (DEVICE): the factory shared files are wrapped as `{"componentDefinitions": {"version": 2, "importFiles": [...], "localComponentDefinitions": [...]}}` (`Generic Text Overlay.json`, `.hw-local/mpc-perf/native-text-contract-xl-20261124/`; the KB note `theme-and-wrappers.md:46` flags this). The SDK text says the file's top level IS the object (`version`, `importFiles`, `localComponentDefinitions`) with no wrapper. CONFLICT SDK vs device; copy the device shape (wrapped), the SDK shape is HYPOTHESIS-only for a third-party file.
- Nesting: SDK says imports load recursively (ui-reference.md:301). DEVICE: the factory `AKAI Generic Components.json` itself imports the Generic Menu/Knob Overlay files (`theme-and-wrappers.md:45`), so nesting works on the device. Cycle behaviour is undocumented: do not nest in a loop.
- Names: a local definition wins over an imported one of the same key; between two imports the winner is undefined (SDK ui-reference.md:304-306). Keep every key unique across all files (our validator already rejects duplicates, `scripts/validate_synthyboy_skin.py`, but only inside `TUI.json`).
- Images in an imported file: relative to THAT file's folder (SDK ui-reference.md:310, 2192-2194). Our shared PNGs sit next to `TUI.json`; a definition in `defs/x.json` must reference `../name.png` (a `..` image path is not documented; HYPOTHESIS) or the PNGs must be copied next to every importing file.
- Tabs: NOT splittable by any host mechanism. `pageData.tabs` is one array in `TUI.json` (max 32 tabs, 8 sub-tabs per key, ui-reference.md:419-421). A tab (version 2/3) only names a root component by `componentName`, and that component is a definition (ui-reference.md:413). So the tab BODY (the whole screen) can live in an imported file; the tab list entry (`tabName`, `fnKeyIndex`, `qlinkBoundsData`, `componentName`, `initialSize`) stays in `TUI.json`. `PartialDescription` is a different thing (one tab repeated by parameter offset, ui-reference.md:359-366) and not a split mechanism.
- Failure modes: a missing import is silent and contributes nothing (SDK ui-reference.md:94, 301): the tab whose `componentName` lives in it has no root (blank), the shared type used inside draws nothing (unknown type = empty, ui-reference.md:92), no error. A parse error: SDK says a `TUI.json` that fails to parse leaves the plugin with no tabs and no default skin (ui-reference.md:91, 96-98); for a broken IMPORTED file the SDK is silent (HYPOTHESIS: that file's definitions are lost like a missing one, or the whole skin fails). Paths are case-exact on the Linux host. Load order across files is undocumented; with unique keys it should not matter.
- Freeze incident (above): it was caused by a definition change inside one `TUI.json`, nothing in it involves importFiles. Splitting changes how many files the host opens while loading and the order definitions are registered; whether the XL load freeze depends on that is HYPOTHESIS. Rule: the split must be a pure move (the union of definitions, key by key, byte-identical to the last working skin) and goes to the Key 61 first.
- Our own tooling: `scripts/validate_synthyboy_skin.py` merges `TUI.json` with its `importFiles` as the host does and rejects a missing, nested, non-flat or unwrapped import file and a `skin/defs_*.json` that is not listed; `scripts/build-mpc.sh` copies the whole `skin/` tree with `cp -R`, `scripts/install-mpc-package.sh` hashes and tars the whole `Plugin Skins` tree (subfolders survive). The layout of our skin: [docs/MPC.md](../MPC.md), skin section; the screens: [docs/ui-components/screens/README.md](../ui-components/screens/README.md).

Verdict (path -> status):
- Definitions in files via `importFiles`, relative path, version 2: SDK-documented and factory-proven on the device; for a third-party plugin folder MEASURED on the Key 61 (see "Measured" below); XL not yet checked.
- Absolute `/nvme/...` or `/sdcard/...` path: NOT usable (the two devices differ; community only shows absolute paths into the factory `/usr/share/Akai/Content/Synths/`).
- Tab bodies as imported definitions (tab entry keeps `componentName`): usable in principle (SDK), same UNKNOWN.
- The `tabs` array / `info` / `replacementStrings` in separate files: NOT usable (no mechanism).
- Wrapper shape of our own imported file: the device (wrapped) shape is REQUIRED; the SDK (unwrapped) shape did not resolve on the Key 61 (see "Measured").

Measured (Key 61, 2026-11-28, run by the coordinator with a trial skin and the real plugin folder; the raw evidence belongs under `.hw-local/mpc-perf/`, the XL has not been checked):
- FACT (measured): an import file in the WRAPPED shape `{"componentDefinitions": {"version": 2, "importFiles": [...], "localComponentDefinitions": [...]}}`, loaded from a relative path (`defs/lfo.json`, next to `TUI.json`), resolved its definitions.
- FACT (measured): the UNWRAPPED SDK shape (`{"version": 2, "importFiles": [...], "localComponentDefinitions": [...]}` at the top level, as `ui-reference.md` section 3.2 describes it) did NOT resolve at all. The SDK text is wrong for a third-party skin here; copy the factory (wrapped) shape.
- FACT (measured): image paths inside an imported file resolve relative to the IMPORTED FILE'S folder (as `ui-reference.md` says). Two runs: a wrapped file at the skin ROOT next to `TUI.json` and the PNGs (`"importFiles": ["lfo_defs.json"]`) resolved all 43 imported definitions AND their images, the LFO tab drew identically to the inline skin; the same file in `defs/` resolved the definitions but showed no images, because the PNGs are in the skin root.
- Consequence: put import files in the skin root (flat) while the PNGs stay there, or rewrite image paths in the build (`../name.png` was not measured). A `defs/` folder is free only for definitions without images.
- Still UNMEASURED: nesting (an imported file importing another), the local-wins duplicate-key rule on a third-party skin, `../x.png`, the XL, load time / freeze behaviour of a split skin versus the single file.

ONE minimal measurement that settles all UNKNOWNs (not run; Key 61 first, then XL, any trial skin, plugin folder with the real plugin): a skin with 4 tabs. `TUI.json` `importFiles: ["defs/a.json", "defs/b.json"]`. `defs/a.json` is wrapped like the factory files, imports `c.json` (same folder), defines tab root `tabA` (a coloured Label plus an Image `a.png` that sits in `defs/`) and a key `dup` (red). `defs/b.json` is SDK-unwrapped and defines `tabB` (green Label). `defs/c.json` defines `tabC`. `TUI.json` defines locally `tabD` and its own `dup` (blue), and tab D's second child uses the type `dup`. Read: tab A visible and image drawn (relative path, wrapped shape, image relative to the imported file); tab B visible or blank (unwrapped shape); tab C (nesting); the colour of `dup` (local wins); plus once a `../x.png` image reference from `defs/a.json`. Record the result and raw photos under `.hw-local/mpc-perf/` and correct this section.

Layout in use: `TUI.json` keeps `pageData.tabs`, `info`, `replacementStrings` and the 37 tab entries; the definitions live in 13 import files in the skin ROOT (not `defs/`: the PNGs sit there, see "Measured"), wrapped factory shape, listed flat in `importFiles` (one level, no nesting), version-2 relative paths, globally unique keys, the PNGs next to `TUI.json` (image paths unchanged). A failed import is silent and produces blank tabs, so the validator checks every listed file.

## Gating a cell on a text line (2026-11-28, UNVERIFIED on a device)

- Hypothesis: `NonZero/Parameter N` on the value of a text-display parameter does not follow "the line has text": the text lines publish a changing fraction in (0, 1] and a line that was never set reports its initial value, and the Key 61 showed the keyline of the Targets title on Play (photo `kbfix-composed.png`). The SDK (`ui-reference.md` 7.4) documents NonZero only for numeric parameters.

- Open: confirm on the Key 61 that the Play line is gone (`TODO.md`).

- FACT (Key 61 and XL, 2026-11-28, package of develop e3693360+): the full skin split into 13 wrapped import files at the skin root (`skin/defs_<family>.json`, 539 definitions, `TUI.json` keeps tabs, info and an `importFiles` list) loads and renders on both devices: Play on both, LFO 1 on the Key 61; the XL resolved the imports as well. The SDK `tools/validate.py` does not follow `importFiles` (it reads only TUI.json), so it cannot catch a missing import file: `scripts/validate_synthyboy_skin.py` merges and checks the files.


## Tab switch cost follows the tab entered, not the other tabs (Key 61, 2026-11-28)

- Measured: Env 1 <-> LFO 1 takes the same time (0.42-0.50 s / 0.31-0.41 s) whether the Osc tab is full (about 2600 expanded nodes) or has its two big layers emptied, so a plugin-wide cache or a smaller tree in OTHER tabs does not speed a switch; only the tree of the tab being entered does. Evidence: `.hw-local/mpc-perf/key61-inactive-tab-cost-20261128/README.md`.
- The cost of entering a tab is the host building its expanded tree: closed (hidden) layers count in full, and a definition with `"repeats": N` counts N times. The Osc tab: ~0.7 s of ~1.3 s was the closed Detail layer (`.hw-local/mpc-perf/key61-osc-pattern-20261128/README.md`).
- A plugin-side state mirror (read-only cache on leaving a tab) only removes the blank first frame; it does not shorten the host's build.
- Open (no source, not measured): whether a skin mechanism exists that does not build the closed parts of a tab (`SubTab/N`, `PageIndex`, the `Local/.../layer` state): `Local` layer id other than `synthyboyWarpPage` is not proven (validator warning).

## A Label drawn above a control takes its touch (Key 61, 2026-11-28)

- FACT (Key 61, MPC 3.10.1.12, owner's finger, 2026-11-28): the Osc header cells TYPE, SOURCE, BROWSE and ROUTE did not react while the full-width `Native Osc Detail Title` Label of `oscScreenTop` (`140 4 1130 56`, `acceptsHWFocus: "No"`, no gate, empty text, later in paint order than the header) lay over them. After the Label took its presence gate (`IndexedEnabling/1/2/Parameter 3901`: exactly 1 while the title has text, 0 while empty) TYPE opens its list and the choice applies. A Label is a touch target for the host even when it shows no text and accepts no focus; a gated-off Label is not. POWER (x 83..123), outside the Label, was not on the fault list. Evidence: `.hw-local/mpc-perf/key61-osc-header-touch-20261128/README.md`.
- Rule: a Label or Image that is later in paint order than an interactive control and overlaps it must be hidden by a gate whenever the control is usable (or be moved below the control in paint order). Text lines that own a keyline use their `Text Present` gate (`nativeui::kTextGate`).
- FACT (same device, same day): the focus chain alone did not restore the touch. Package `oschdr-focus-c33c2796` (header forms `ignoreMousePresses: true`, Osc header instances `acceptsHWFocus: "Children"`, action cells `"Yes"`, inner-Button cells and the ROUTE wrapper `"Children"`) with the Label still ungated: TYPE did not react.
- NOT MEASURED: the Label gate without the focus chain changes. Both are in the working package `oschdr-titlegate-cb7bd5b1`, so whether the header focus chain of commit `d8869ad4` (`ignoreMousePresses: false` forms, cells `"No"`, instance `"Yes"`) would also work under a gated Label is unknown. The chain now in the skin is the one of the pre-header skin and of the Voice header.
- XL: not checked yet.

## Handle remapping of nested components: Data must be mapped, modifiers go on `Parameter N` (Key 61, 2026-11-28)

Measured with marker Images and three probe skins on the Key 61 (MPC 3.10.1.12); evidence and captures: `.hw-local/mpc-perf/key61-osc-header-touch-20261128/README.md`.

- FACT: an instance of a custom component whose `handle remapping` map is NON-EMPTY but has no `Data` entry, with `showWhenDataModelInvalid: "Hide"`, is hidden as a whole, even while its gate is true. `Osc Native List` (remap `Row0..`, `Gate0..`, `Back`, ... and no `Data`) drew nothing while its gate `IndexedEnabling/1/2/Parameter 3588` was true (a marker Image with the same gate next to it was lit). Adding `Data -> Parameter 3588` made its plain-alias child (the Title Label) appear. Instances with an EMPTY map are not affected (they pass the parent's Data).
- FACT: inside a definition, a modifier expression over an alias name does not resolve: `FromGesture/Back`, `IndexedEnabling/1/2/Gate0`, `IndexedEnabling/0/2/Title`, `WithName[]/Row0` left their components hidden (`Hide`). A plain alias (`Title`, `Row0`) resolves through the parent's remap. The same expressions written on a real parameter in the INSTANCE remap (`Back -> FromGesture/Parameter 3584`, `Gate0 -> IndexedEnabling/1/2/Parameter 3590`, `Cap0 -> WithName[]/Parameter 3577`) and referenced by plain alias in the definition work: the list shows BACK, UP, the rows and the pagers, a row tap applies and closes, BACK returns.
- Rule: definitions use plain alias names only (in `handle remapping` values and in `additionalInvalidatingHandles`); every modifier (`FromGesture/`, `IndexedEnabling/`, `RangedEnabling/`, `NonZero/`, `WithName[]/`, `ResetOnGestureEnd/`) is applied to `Parameter N` at the outermost instance; an instance with a non-empty remap always maps `Data`.
- FACT (same probes): `NonZero/Parameter 3588`, `NonZero/Parameter 3590` and `NonZero/Parameter 3584` were true both while the list was closed (the plugin reports 0 for the gate, `IndexedEnabling/0/2/Parameter 3588` true) and while it was open. `NonZero` did not act as a 0/1 gate on these plugin-written handles; use `IndexedEnabling/1/2/` on an exact 0/1 value.
- OPEN: a row tap sometimes has no effect ("Square" twice in one opening, then "Triangle" at the first tap of the next opening). HYPOTHESIS: the rows are `Toggle Switch` cells, so a row left at 1 by an earlier tap goes to 0 on the next tap, which the plugin ignores (`value < 0.5`). Check: tap the same row twice in one opening and read the cell value.
- Not checked: the XL; the Env and Filter instances of the list (changed the same way, not opened on the device); the Targets pages (Env TARGETS is still an empty body, `page_top: 30`).

## The stock Fabric XL lists: grouping and one-tap choice (Key 61, 2026-11-28)

Captures and steps: `.hw-local/mpc-perf/key61-fabric-lists-20261128/README.md` (host plane, taps injected with mtouch, one run; XL not checked).

- FACT: Fabric XL groups its sounds with two separate parameters and two flat lists per layer: the category ("LAYER 1 BANK": Acoustic Guitars, Electric Guitars, Bass Guitars, Pads + Polys, Synth Hard, Synth Bass, Leads, Oscillators, FX, ...) and the preset of that category ("LAYER 1 SAMPLES"). Choosing a category replaces the content of the preset list and the preset (Synth Bass / Detune Fuzz -> Leads / Fat Square). No tree, no UP / GROUPS button, no pager; the list scrolls. Skin side: `sample1Header` holds `comboBank1` and `comboSamplesSample1`, each `Double Click` / `Enter Pressed` -> `Show Overlay` `menu overlay` (reference skin `.hw-local/mpc-ui-plans/reference-skins/MPC_-_Fabric_XL.TUI.json`).
- FACT: the list is the host's left drawer: 426 px wide, a header with the parameter name, plain text rows 80 px high, the current row highlighted with a check mark, a thin scroll bar, the page behind blurred and dimmed. It opens on a double tap of the field (a single tap only assigns the Q-Link).
- FACT: for this stock plugin ONE tap on a row applied the choice and closed the drawer. This differs from what the Key 61 probes A/B of 2026-11-27 measured for our VST2 skin (a row tap only moved the check mark, the header tap applied); why the same host list behaves differently for a stock plugin is not known.
- FACT: the host plugin picker (PLUGIN field held about 900 ms) is the host's grouped list: a centred dialog with collapsible groups (+ / -) by MANUFACTURER or TYPE; there a row tap only highlights and SELECT applies.
