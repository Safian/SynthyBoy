# ARM Denormal Protection (MPC Key 61 and MPC XL)

## Render Entry Point and FP State Scope

- The MPC VST2 shell exports `VSTPluginMain` (`shell-mpc/synthyboy_mpc.cpp`) and registers `pluginProcessReplacing` (`effect->processReplacing`); `process` and `processDoubleReplacing` are null.
- `pluginProcessReplacing` queries host transport (`audioMasterGetTime`), drains/sorts `EventInbox`, and then enters `synthyboy_mpc::FlushDenormalsScope` (`shell-mpc/denormal_scope.h`) around an out-of-line (`__attribute__((noinline))`) `renderAudioBlock` call that runs `OwnEngine::process`, `OutputStage::process`, `OutputPeak::note`, and `SpectrumRing::push`.
- Placing `FlushDenormalsScope` after `audioMasterGetTime` ensures host callbacks run in the host's FP mode and cannot clear `FZ` before `OwnEngine::process`. Calling `renderAudioBlock` out-of-line prevents compiler code motion of inlined `OutputStage` / `OutputPeak` register arithmetic across the `FPCR`/`FPSCR` writes (observed on Apple Clang `arm64` `-O2`: register-only `fmul` instructions with a live result read after the scope were sunk past `msr FPCR` when only a `"memory"` clobber separated them). `test: shell-mpc/tests/arm_denormal_check.cpp`

## ARM32 (`armv7`, Key 61) vs AArch64 (`arm64`, MPC XL)

- **ARM32 (`__arm__`, Cortex-A17):**
  - `FPSCR.FZ` (bit 24, `0x01000000u`) controls VFP scalar/vector floating-point flush-to-zero for single- and double-precision arithmetic; `VMSR FPSCR` acts as a VFP exception/serialization barrier for subsequent VFP instructions. `source: ARM DDI 0406`
  - Advanced SIMD (NEON) on ARMv7-A always operates in flush-to-zero mode regardless of `FPSCR.FZ`. Without `FPSCR.FZ = 1`, VFP scalar code preserves subnormals while NEON flushes them, which would both risk VFP subnormal slowdowns and break bit-identity between VFP and NEON lanes. `source: ARM DDI 0406`
- **AArch64 (`__aarch64__`, RK3588):**
  - `FPCR.FZ` (bit 24, `0x01000000ull`) controls flush-to-zero for both scalar FP and Advanced SIMD (NEON) instructions (`FPCR.AH == 0` flushes both subnormal inputs and tiny results for single and double precision). Unlike ARMv7 NEON, AArch64 NEON preserves subnormals when `FPCR.FZ == 0`. `source: ARM DDI 0487`; `test: arm_denormal_check` (`arm64`)
  - Direct writes via `MSR FPCR` are self-synchronizing for subsequent FP/SIMD instructions on the same PE. `source: ARM DDI 0487`
- **Non-audio / helper threads:** `OwnEngine` helper threads (`WavetableBank`, `FxPool`, `Convolve` IR prep) perform offline setup rather than block rendering and intentionally keep the default IEEE FP mode.

## Core Software Guards

- Recursive core DSP modules additionally apply `synthyboy::own::flushDenormal` (`|v| < 1.0e-18f ? 0.0f : v`, `core/engine-own/dsp/util.h`) and `neoncmp::flushTiny` (`core/engine-own/dsp/neon_cmp.h`), which behave identically in IEEE and `FZ=1` modes because `1.0e-18f` is a normal float (`test: core/tests/test_neon_cmp.cpp`, `shell-mpc/tests/arm_denormal_check.cpp`).

## NEON float compares as integer compares (`core/engine-own/dsp/neon_cmp.h`)

- GCC for 32 bit ARM emits no `vcgt.f32` / `vclt.f32` family without `-funsafe-math-optimizations` (NEON flushes subnormal inputs, IEEE does not), so a raw `vcltq_f32` etc. becomes scalar VFP code per lane. Every compare of the vector paths is therefore made on the bit patterns, with integer instructions, on both architectures. `source: CPU review F2, neon_cmp.h header`
- Forms and their exact meaning: the constant forms (`absLt`, `absLe`, `geConst`, `leConst`, `gtConst`, `absGeConstFinite`; constant a normal number) and `ltZero` (x < 0), `belowTruncation` (x < float of its own truncation) are the IEEE compares for **every** bit pattern (NaN, infinities, both zeros, subnormals). The general forms (`lt le gt ge eq`) are the IEEE compares of two vectors. `gtNonNeg` / `geNonNeg` are the compares of two operands that are +0, normal or +infinity (`nonNegNormalOrZero` tests that), and nothing else. `test: core/tests/test_own_neon_compare_sites.cpp` (all 2^32 patterns with `SB_TEST_FULL=1`), `core/tests/test_neon_cmp.cpp`
- A compare with zero cannot be made independent of the float mode: for a negative subnormal the IEEE compare says "below", the flush-to-zero compare "not below". `ltZero` and `belowTruncation` are IEEE. Each site must not depend on a subnormal operand, and says why: the sine / cosine quadrant (`kernels.cpp sincosN`: `a * 2/pi +- 0.5` converts to 0 for a subnormal `a` either way), the phase wrap (a selected lane has |x| > 100, its remainder is a multiple of the ulp of |x|), the oscillator wrap `w < 0` (the phase is a multiple of 2^-24 or a result of arithmetic on one) and the floor correction (`ffloor4`, |x| < 2^22 not subnormal). `measured: not applicable (exhaustive test)`
- Domain-checked sites: `kernels.cpp findPeaks` (vector form only when every bin it reads, and the threshold, satisfies `nonNegNormalOrZero`; otherwise the scalar loop) and `placeRegion` (four bins that do not satisfy it go through the scalar compare). The vector form is therefore the scalar form for every input, in IEEE and in flush-to-zero mode. `test: core/tests/test_own_spectral_lanes.cpp` (mutation checked: removing either domain test fails it)
- The NEON of 32 bit ARM always produces the **default NaN** (positive quiet NaN, payload 0) and flushes subnormals, whatever `FPSCR.FZ` says; the VFP scalar code propagates the NaN operand's payload and keeps subnormals unless `FZ` is set. Vector-versus-scalar tests on 32 bit ARM therefore compare a NaN as "a NaN" and run in the flush-to-zero mode (the mode of the shell). `test: core/tests/test_own_simd_lanes.cpp`, `test_own_spectral_lanes.cpp` (`core/tests/fp_flush_mode.h`); `core/tests/test_own_mix_lanes.cpp` compares NaN payloads and stays 64 bit only
- `vmaxq_f32` / `vminq_f32` (and the AArch64 `fmax`) return a NaN where an operand is a NaN, `std::max` / `std::clamp` keep the other operand; and in flush-to-zero mode they flush a subnormal operand where `std::clamp` passes it on. `kernels.cpp maxBins` masks the NaN lanes first. **Open finding:** `simd::clampTo` (the voice filter output clamp, `dsp/simd.h`) gives a zero of the same sign where the scalar `std::clamp` keeps a subnormal sample, in flush-to-zero mode only (below 1.2e-38, inaudible; not bit identical; measured under qemu-user on both ARM forms). `test: core/tests/test_own_simd_lanes.cpp` (the data of that mode has no subnormals there). `granular.cpp clampFinite` clamps the raw sample the same way: HYPOTHESIS that it shows the same difference (not measured). `kernels.cpp gainClamp` clamps a product, which the flush-to-zero mode flushes first: no difference (tested)
