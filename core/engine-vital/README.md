# engine-vital

Vital-derived DSP behind `synthyboy::IEngine`. Everything that contains Vital-derived code lives in this directory and
nowhere else (docs/ARCHITECTURE.md 2.2); it is built only with `-DSYNTHYBOY_WITH_VITAL=ON` (default; forced OFF for iOS,
where `scripts/check-no-vital.sh` checks the static library).

```
upstream/   the imported Vital sources (GPL-3.0-or-later, namespace sbvital), every change listed in docs/UPSTREAM.md
compat/     vital_compat.h: what JuceHeader.h used to provide (std headers, no-op leak detector, base64)
adapter/    our code (AGPL-3.0-or-later), compiled into synthyboy_core when SYNTHYBOY_WITH_VITAL=ON (the imported DSP is the static
            library synthyboy_engine_vital, which depends on nothing of ours):
              vital_engine.{h,cpp}    the IEngine implementation
              vital_bindings.{h,cpp}  the table parameter -> engine control, one converter per kind (Vital-free header)
              vital_tables.{h,cpp}    the built-in wavetables and LFO shapes, generated by code
tests/      adapter tests (feature "golden" measurements, FFT) and the ported Vital unit tests (tests/synthesis/**)
```

`createEngine (EngineKind::vital)` (core/include/synthyboy/engine.h) returns the engine, or `nullptr` plus an error text if
the build has no Vital. The JUCE shell uses this engine by default and the own engine with `-DSYNTHYBOY_SHELL_ENGINE=own` (or when the
build has no Vital).

## What the adapter does

The parameter table (core/src/param_table.cpp, docs/PARAMETERS.md) is ours; this directory maps it onto the controls of the engine.

`prepare()` (the only call that allocates) builds a complete `sbvital::SoundEngine`, the 13 built-in wavetables (once per engine
object) and the tables of the modulation matrix, sets the sample rate and 120 BPM, applies the quality's oversampling (1x or 2x, fixed
for the life of the engine's buffers), applies every parameter, and renders two short notes so that lazily built tables exist before
the audio thread runs. About 30 to 70 ms on an M-class laptop, 170 MB resident for one engine (the engine's three wavetable slots, its
buffers and the built-in tables; Vital's own memory use).

`process()`
1. copies the parameters that changed since the last block into the engine's controls (change detection: one atomic load and one
   compare per parameter; the conversion runs only for the ones that changed), applies the quality hand-off (`setQuality`), the
   special parameters (wavetable and LFO shape choice, filter routing, FX order) and wires / unwires the modulation slots;
2. cuts the host block at every event frame and into pieces of at most 128 frames (`sbvital::kMaxBufferSize`), applies the events between
   the pieces and converts Vital's interleaved `poly_float` output (lanes 0/1 = left/right) to left/right;
3. sets flush-to-zero around the call and restores the caller's mode.

### Parameters (vital_bindings.cpp)

730 parameters map onto exactly one control through one of ten converters (`Conv`): linear (`plain * a + b`), square root of a scaled
percentage (the engine's "quadratic" controls: levels, unison detune, EQ resonance, reverb chorus), fourth root of seconds (envelope
times), log2 of seconds / of Hz / of the frequency 1/time (LFO and effect rates, delay times, portamento, smoothing), MIDI note of a
frequency in Hz (every cutoff, limited to 0.45 x the sample rate), choice index with an offset or a map (the warp types: our list
leaves out the two variants that need the sample oscillator), and the master volume (`value = (dB + 80)^2`, -60 dB and below = silence).
The converted value is clamped to the control's own range (read from the engine's value details). A test checks, for every parameter at
its minimum, default, maximum and along a sweep, that the conversion is inside that range before clamping (a few end exactly on a bound),
and that the value arrives in the engine's control.

150 parameters are special:

| Parameters | Handling |
|------------|----------|
| `oscN.wavetable` | the oscillator's wavetable is pointed at one of 13 pre-built tables (`Wavetable::useExternalData`, between blocks, no allocation); all tables are 1 frame (the basic shapes) or 64 frames (the morphs), so `oscN.frame` is a position over 64 frames |
| `lfoN.shape` | the LFO's line is set to one of 12 shapes and rendered (no allocation) |
| `filter.routing` | `filter_1_filter_input` / `filter_2_filter_input` (parallel, series 1 to 2, series 2 to 1) |
| `fx.order.1` .. `fx.order.9` | the nine choices become a permutation (duplicates: a later position takes the lowest effect not yet placed), encoded for `effect_chain_order` |
| `modNN.source`, `modNN.destination` | the slot is wired with `connectModulation` / `disconnectModulation` (below); amount, curve, bipolar, stereo, bypass are plain controls of the slot's connection processor |
| `master.bend_range` | the pitch bend event is scaled with it (the per-channel wheel of the voices, range 48 semitones per unit); the engine's own range control is set to 0 |

Quality tiers (`Quality`, core/include/synthyboy/quality.h) cap the converted values without touching the stored parameters:
`master.polyphony` -> `min (polyphony, maxVoices)`, `oscN.unison.voices` -> `min (voices, maxUnison)`, an effect's `on` is 0 if the tier
bypasses it, `smooth_interpolation` of the oscillators follows `Quality::interpolation`. `setQuality()` is a lock-free hand-off
(atomics), taken over at the start of the next block; `Quality::oversampling` is applied by `prepare()` only (it sizes the buffers).

### The modulation matrix on the audio thread

The 64 slots are the engine's 64 connection processors. A slot with a source and a destination is wired by the audio thread at the start
of a block, a changed one is unwired first. Wiring allocates in the engine in three cases, all handled (docs/UPSTREAM.md, "What the
modulation matrix does on the audio thread"): free inputs are reserved at every destination at `prepare()`, the work queues of the
routers are grown at `prepare()`, and a slot whose wiring would close a loop (its source depends on its destination) is left unwired
(the engine would insert a feedback node, which allocates). Tested with a counting `operator new` and random matrices: no allocation.
An amount of 100 % is a full sweep of the destination's range **in the engine's own scale** (cutoffs in semitones, times through the
engine's curve, ...), documented in docs/PARAMETERS.md.

### Events (core/include/synthyboy/events.h)

`SustainPedal` (per channel or all channels: the engine's sustain), `NoteOff` carries the release velocity (the "Lift" source),
`NoteExpression` (tuning in semitones = per-note pitch, pressure = "Poly Aftertouch", brightness = "Slide"; addressed by host note id or by
channel and key, key -1 = every note of the channel). `IEngine::setTransport` feeds the tempo (`setBpm`, the beat units of the envelopes and the
tempo sync of everything else) and the song position (LFO host mode). Expressions are applied whatever `master.mpe.on` says (they are explicit
data of the host); `master.mpe.on` decides what the MIDI channel messages mean (below). `NoteOn` (velocity 0..1; a still-ringing note of the same key is released first, as in the own engine), `NoteOff`, `PitchBend` (per
channel, +-`master.bend_range` semitones; also feeds the "Pitch Wheel" source), `ModWheel` (per channel, the "Mod Wheel" source),
`Aftertouch` (channel pressure, the "Aftertouch" source), `AllNotesOff` (all channels, or one channel).

## Behaviour that differs from the own engine (measured, see core/tests)

* Level: at the same gain the Vital engine is about 2.4x (7.4 dB) louder (its signal chain is calibrated differently).
* Velocity curve: amplitude ~ velocity squared (Vital's `velocity_track` interpolation); the own engine is linear.
* Release: the default patch has a 200 ms release (own: 250 ms); both end in exact zero and 0 voices.
* Voices: `activeVoices()` counts released voices that still fade out and stolen voices during their 50 ms kill fade, so it can
  exceed the voice limit for a moment when notes arrive faster than they fade (at most 34 seen with 32 allowed).
  The number of *sustaining* voices never exceeds the limit.
* Block size: without pitch bends the output does not depend on the host block size (relative RMS difference below 3e-6,
  because the block is cut at every event); a bend that arrives while a note sounds moves Vital's control-rate pitch
  over the processed piece, so its shape depends on how the host splits the stream (relative RMS difference up to 12 %
  for a sine between 1-sample and 4096-sample blocks).
* `reset()` renders 100 silent pieces (12800 frames) so that Vital's smoothers sit on the current parameter values; the
  next render equals the first one up to about 1.3e-5 relative RMS (voice filters keep tiny residues), not bit for bit.
  Two freshly prepared instances render bit-identical output.
* Determinism: the random generators of the engine (noise, random LFOs, random phase) are seeded from a counter that `prepare()` starts at 0 on its
  thread (docs/UPSTREAM.md): two engines with the same parameters, prepared the same way, render the same bits.
* Note offsets inside a piece are not sample accurate in Vital (the `sample` argument of `noteOn` does not delay the
  audio), which is why the adapter cuts the block at every event frame instead.

## Real-time rules

`process()` does not allocate (tested with a counting `operator new`: all tiers, random parameters of every kind, a matrix that is
rewired every block, quality changes), takes no locks (the imported code has none) and throws nothing. Parameter changes are atomics,
copied into Vital's controls at the start of a block on the audio thread. The global singletons of the imported code
(`PredefinedWaveFrames`, `FFT<bits>`) and the first-use tables are initialised in `prepare()`.
